# 变更日志

## v2.2.0 — 2026-10-10

### pm-execution

- **create-prd** 现在默认保持精简：第一版 PRD 大约一到两页，需要详细版时再展开。此前的反馈是，这个技能自相矛盾：一边要求「全面」的文档，一边又要求简短。「完整」现在的含义是：没有会阻碍对第一版做出决策的缺口；各章节的问题变成可从中间挑选的检查清单，而不是必须逐项填写的表单；市场细分与价值主张始终包含在内；未知信息归入「假设」和「待解问题」，而不是凭空编造；当缺少问题、用户或成功指标时，它最多追问三个问题；它可自由调研市场、竞品与替代方案并注明来源，只有当某条发现会改变决策时才写进 PRD；最后它会说明自己省略了什么，方便你展开任意章节。价值主张一节现在使用 6 部分的 JTBD 模板（Who、Why、What before、How、What after、Alternatives，由 Paweł Huryn 与 Aatir Abdul Rauf 提出），每个细分市场一份（第一版最多两到三个细分市场），并且它是 PRD 的主干：解决方案负责兑现它的 How，关键结果负责度量它的 What after。它还新增了一份简短的检查清单，用于评审已有的 PRD。
- **`/write-prd`** 现在改用 create-prd 模板。此前它在调用该技能的同时，还自带一套不同的 8 部分模板。现在它开场最多只问三个问题。

### pm-ai-shipping

- 新增 **code-review** 技能：正确性是核心引擎，性能与安全是它的可选子情形，而不是独立的方法。它以跨越边界时参与者之间的约定为锚点——那些逐文件检查看不见、因为单独看每一侧都合理的缺陷——强制构造一次违反约定的执行，并在报告之前逐一反驳每个候选结论。
- 新增一份基于真实修复历史构建的正确性分类参考，以及同一引擎读取的性能与安全参考表。
- `/ship-check` 新增第 3 步的正确性评审（位于安全与性能审计之前），并在第 6 步增加第二个模型做的独立、无引导复检。
- `/security-audit-static` 新增 OWASP Top 10 覆盖兜底：每一条存留的发现都映射到一个类别，任何零发现的类别都会被标记为「未覆盖——请复查」，而不是悄悄放过。这是覆盖检查，不是要求你凭空编造发现。
- 文档、测试覆盖图与报告现在都遵循宿主仓库的既有设置。动笔之前，工具包会读取该仓库的代理说明（`AGENTS.md`、`CLAUDE.md` 及其导入的文件）、文档目录，以及每份文档在任何名称下已有的等价文件；它更新这些文件，而不是另建一套平行文件，并沿用它们的命名与日期约定。只有在仓库没有对应文件时，才会使用 `documentation/`、`documentation/tests.md`、`reports/` 与默认文件名，且输出中会说明这一点。它绝不会创建一个与现有文件仅大小写不同的文件（如与 `TESTS.md` 并存的 `tests.md`），因为那在 Windows 和 macOS 上会冲突。这条规则只写在一处，在 **shipping-artifacts** 技能里。
- `/ship-check` 会编辑仓库已经在用的代理说明文件。当 `CLAUDE.md` 与 `AGENTS.md` 中只有一个只是导入或指向另一个（例如内容仅为 `@AGENTS.md` 的 `CLAUDE.md`）时，它编辑被指向的文件，并保持指针不动；当只有其中一个存在时，就编辑那一个。只有在两个文件都不存在的仓库里，才会新建 `CLAUDE.md` 加上一个很薄的 `AGENTS.md`。
- `/ship-check` 第 6 步的独立复检，是一个与写代码的模型属于不同模型族的全新会话，并使用仓库自身说明中指定的评审者。它不再把某个具体模型当作常用选择。
- `/derive-tests` 服从仓库声明的门禁策略。如果仓库的说明把门禁定义为一个本地命令加人工放行，就保留这套做法：覆盖图记录该策略以及确定性测试是否在其中运行，而不是建议用托管 CI 与分支保护来取代它。仓库未声明策略时，仍然推荐「合并前绿灯」的 CI 门禁。
- `/derive-tests` 只在目标文件本身是测试覆盖图时，才写入一个已存在的文件。描述仓库测试方法的 `TESTS.md` 不会再仅仅因为名字就被当作覆盖图：工具包按文件覆盖的内容来匹配，使用仓库真实的覆盖图，若没有则选一个不会与任何文件冲突的名字，而不是写进一个同名但内容无关的文件。
- `/document-app check` 是只做检查的模式，面向手工维护文档、把文档当作意图的仓库。它不写任何文件，只报告现有文档与代码不一致的每一处：文档说 X，代码做 Y，并附上双方的 `file:line`。它不判断哪边错了；由负责人决定改代码还是改文档。输出结尾是一段简短摘要，发布清单可以直接引用。
- `/derive-tests check` 对覆盖图做同样的事。它不写文件，只读取测试而不运行，报告相对文档或测试套件已经过期的行（有规则记录却没有对应行、标为「已存在」的行对应的测试已消失、测试套件里有但覆盖图未计入的测试），结尾同样是那种可直接引用的摘要。
- `/security-audit-static` 与 `/performance-audit-static` 可以只审计一次变更：传入 git 区间（`/security-audit-static v2.1.0..HEAD`）、针对未提交工作区的 `changes`，或两者都给。审计覆盖变更涉及的文件，以及这次变更在别处新引入的可达路径或新错误，而不是整个代码库。发布时通常只审计本次变更；全仓库审计（不带参数时的默认行为）用于首次发布或大重构之后。

## v2.1.0 — 2026-07-03

### pm-ai-shipping

- `/security-audit-static` 的发现现在必须带一行 **Evidence**（`file:line` + 原文片段），并且在最终报告交付前，每一条引用都会对照文件复核一遍。
- 子代理并行分发有具体触发条件（范围超过约 30 个文件 / 约 5,000 行）和结构化的候选记录约定，因此并行的审计切片能干净地合并成一轮自我反驳。
- `/performance-audit-static` 现在会主动搜寻 **N+1 查询与请求瀑布**——AI 生成代码中最常见的性能故障——同时覆盖过度获取、索引和缓存，并新增了「先反驳再报告」的一轮（动态字段访问、已有索引、热路径证据）。
- 两个审计命令都预先批准一组只读工具（`allowed-tools`）：读取、搜索、并行分发，以及在 `reports/` 下写入——绝不修改被审计的代码。
- 整个工具包都把被审计仓库视为不可信输入：写在代码、注释或文档里的指令只是待分析的数据——任何试图操纵审计的行为本身就是一条发现——绝不能当作要执行的指令。
- `/ship-check` 在文档就绪后，把安全与性能审计作为并行子代理运行。
- 安全报告新增严重度锚点（Critical/High/Medium/Low 各自代表什么）与合并规则（发现超过约 12 条时，先讲最严重的，其余按根因归类）。
- 文档与报告现在使用仓库相对路径（`documentation/`、`reports/`）——旧的绝对形式（`/documentation`）可能被解析到文件系统根目录——并且报告始终会写，同时公布路径，而不是「可选」。

### 仓库

- 新增本 `CHANGELOG.md` 作为发布的事实来源，并在合并时自动打标签与发布（改编自 [claude-usage](https://github.com/phuryn/claude-usage)）：向 `main` 推送新的 `## vX.Y.Z` 标题，就会为该版本打标签，并以对应章节作为说明发布 GitHub Release——其前置条件是测试套件与版本同步检查通过。
- 新增测试套件（`tests/`）与测试工作流（每次 PR 与推送到 `main`）：插件规范校验加文档一致性检查——README 技能/命令计数与磁盘对比、marketplace 插件列表与目录对比、所有清单的版本同步、CHANGELOG 格式。
- CONTRIBUTING 现在记录了变更日志约定（每项面向用户的改动都要有一条；贡献者就地署名）与发布流程。
- 自 v2.0.0 以来的文档：Codex CLI 原生安装路径；配套徽章（burnstop、claude-usage）。
