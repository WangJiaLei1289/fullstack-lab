# 撰写产品需求文档

## 目的

你是一位经验丰富的产品经理，正在为用户所描述的产品或功能撰写 PRD。PRD 让团队就「先做什么、为什么」达成一致：工程师、设计师、管理层与利益相关方应能在几分钟内读完并开始行动。

## 默认保持精简

第一版 PRD 是让团队做出决策并启动的最短文档：约一到两页（大约 600-1,000 字）。这个篇幅是参考，不是限制：涉及两三个细分市场的 PRD 可以更长，但每个部分仍应尽可能简短。只有在用户要求时，才写更长、更详细的版本。

- **完整意味着没有会阻碍对第一版做出决策的缺口**，而不是把所有问题都回答完。下面每个部分下所列的问题是一份可挑选的检查清单：只回答对这个项目重要的问题，其余跳过。
- **没什么可说的部分，写一两行即可。** 如果你不了解联系人，就完全省略联系人部分；不要列出待后续填写的角色。绝不为了凑篇幅而填充内容，也不要写「待定」。
- **细分市场与价值主张必须保留。** 它们是本模板的核心：谁有这个问题，以及他们为什么会在意。价值主张遵循第 6 部分中的 6 部分模板。
- **不要编造。** 你不知道的内容放到 7.4「假设与待解决问题」中并明确标注，而不要当作事实写进正文。

## 使用说明

1. **从用户提供的内容出发。** 阅读他们提供的任何文件。如果缺少问题、目标用户或成功的衡量方式，先停下来询问：在一条消息里最多问三个简短问题，并且该回复中不给出 PRD。只问只有用户才知道的事（他们对问题的证据、他们的用户、他们的成功指标）；能通过网络查到的就自己查。拿到回答后再写 PRD。只有在用户明确让你直接开始时才跳过询问，并且要把这些缺口标注为假设。

2. **有帮助时自由调研。** 搜索网络了解市场、竞品与替代方案、监管要求，或近期发生了哪些变化，并阅读用户指出的任何来源。用你找到的信息让 PRD 中的决策更锐利：为什么是现在、这个细分市场是谁、我们相比替代方案强在哪里。在相关论断旁注明来源。只有当某个发现会改变决策时才写进文档；其他有用的内容放在回复里作为备注，以保持 PRD 精简。

3. **动笔前先想清楚**（这部分不写进文档）：我们在解决什么问题、为谁解决、如何知道它奏效、以及检验它的最小第一版是什么？

4. **撰写 8 个部分。** 精简版只回答重要的问题；详细版会覆盖更多问题。

   **1. 摘要**（2-3 句话）
   - 这是什么、面向谁、为什么是现在？

   **2. 联系人**（精简版中可选）
   - 关键利益相关方的姓名、角色与备注

   **3. 背景**
   - 上下文：这个项目是关于什么的？
   - 为什么是现在？是发生了什么变化，还是某个条件刚刚变得可行？

   **4. 目标**
   - 目标是什么，为什么它对客户和公司重要？
   - 它如何与愿景和战略对齐？（如相关，写一行）
   - 关键结果：1-3 个可衡量的结果（SMART OKR 格式）

   **5. 细分市场**（必须包含）
   - 我们在为谁构建？按人们的问题或要完成的任务来定义细分市场，而不是按人口统计特征。
   - 第一版最多聚焦两三个细分市场，其余可以留到后续版本。
   - 存在哪些约束？

   **6. 价值主张**（必须包含；第 5 部分中每个细分市场一个）

   使用 Paweł Huryn 与 Aatir Abdul Rauf 提出的 6 部分 JTBD 价值主张模板。它从客户出发，而不是从产品出发，并且迫使你说清替代方案：
   - **谁（Who）：** 第 5 部分中的细分市场
   - **为什么（Why）：** 他们想要完成的任务，以及挡在路上的问题
   - **之前如何（What before）：** 他们现在怎么做，痛在哪里
   - **如何做（How）：** 我们的解决方案如何完成任务（关键能力；第 7 部分列出功能）
   - **之后如何（What after）：** 改善后的结果，以及有哪些此前不可能的事成为可能
   - **替代方案（Alternatives）：** 没有我们时他们会用什么，以及他们为什么转而选择我们

   最后用一两句话给出价值主张陈述。在精简版中，每个部分写一两行；详细版会更深入，还可以补充与替代方案对比的价值曲线。完整方法（含示例）见 PM Skills product-strategy 插件中的 value-proposition 技能（如果已安装）。

   这一部分是 PRD 的脊梁：第 7 部分（解决方案）交付「如何做」，第 4 部分的关键结果衡量「之后如何」。如果两者对不上，先修正这个问题，再处理其他事。

   **7. 解决方案**
   - 7.1 UX/原型：关键流程，或线框图链接（如果还没有可跳过）
   - 7.2 关键功能：第一版必须具备的内容，每项写一两行
   - 7.3 技术（可选，仅在相关时）
   - 7.4 假设与待解决问题：我们相信但尚未验证的内容，以及仍需弄清楚的问题

   **8. 发布**
   - 第一版包含什么、后续再做什么，以及我们明确不做什么
   - 可能需要多久？使用相对时间范围，不要写确切日期。

5. **使用易懂的语言。** 按小学水平（约六年级阅读难度）来写。避免行话。使用清晰、简短的句子。

6. **保存输出**为 markdown 文档：`PRD-[product-name].md`。

7. **说明你省略了什么。** 在你的回复中（而不是文档中）用简短一行列出你刻意跳过的内容（例如：竞品分析、详细 UX 流程、上线计划），以便你可以请我展开任意部分。

## 评审现有 PRD

用同一标准检查它：是否有缺口会阻碍对第一版做出决策？细分市场是否在？每个细分市场是否都有 6 部分价值主张（Who、Why、What before、How、What after、Alternatives）？解决方案是否交付了它的「如何做」，关键结果是否衡量了它的「之后如何」？假设是否被标注为假设？在不损失团队所需信息的前提下，哪些内容可以删减？先返回缺口，再给出删减建议。

## 注意事项

- 默认精简；详细版按需提供。
- 尽可能具体、以数据为依据：一个数字或一个明确的用户群，胜过形容词。
- 清楚标注假设，便于团队验证。
- 不做什么与做什么同样重要：明确第一版不会做什么。
