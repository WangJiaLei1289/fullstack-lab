## 发布说明生成器

把技术工单、PRD 或内部变更日志转化为打磨过的、面向用户的发布说明。

### 背景

你正在为 **$ARGUMENTS** 撰写发布说明。

如果用户提供文件（JIRA 导出、Linear 工单、PRD、Git 日志或内部变更日志），请先阅读。如果他们提到产品 URL，请使用网络搜索了解该产品与受众。

### 使用说明

1. **收集素材**：阅读所有提供的工单、变更日志或描述。提取：
   - 改了什么（功能、改进还是修复）
   - 影响谁（哪个用户细分）
   - 为什么重要（对用户的好处）

2. **给变更分类**：
   - **新功能**：全新的能力
   - **改进**：对现有功能的增强
   - **缺陷修复**：已解决的问题
   - **破坏性变更**：任何需要用户操作的内容（迁移、API 变更）
   - **弃用**：即将下线的功能

3. **撰写每条记录**，遵循以下原则：
   - 先讲用户收益，而不是技术变更
   - 使用通俗语言——避免行话、内部代号或工单编号
   - 每条记录控制在 1-3 句话
   - 如果用户提供了视觉素材或截图，就一并放入

   **转化示例**：
   - 技术表述：「为仪表盘 API 接口实现了 Redis 缓存层」
   - 用户视角：「仪表盘现在的加载速度快了最高 3 倍，让你少花时间等待，多花时间分析。」

   - 技术表述：「修复并发结账流程中的竞态条件」
   - 用户视角：「修复了高流量时段部分订单可能失败的问题。」

4. **组织发布说明**：

   ```
   # [产品名称] — [版本 / 日期]

   ## 新功能
   - **[功能名称]**：[用 1-2 句话说明它做什么、为什么重要]

   ## 改进
   - **[模块]**：[哪里变好了，以及如何带来帮助]

   ## 缺陷修复
   - 修复了 [用用户能懂的语言描述问题]

   ## 破坏性变更（如有）
   - **需要操作**：[用户需要做什么]
   ```

5. **调整语气**，与产品调性一致——B2B 偏专业，面向消费者偏亲切，面向 API 偏开发者视角。

保存为 markdown 文档。如果用户想要 HTML 或其他格式，就相应转换。
