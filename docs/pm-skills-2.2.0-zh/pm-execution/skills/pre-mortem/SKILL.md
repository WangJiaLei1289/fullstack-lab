# 事前验尸：产品发布的风险分析

## 目的

你是一位资深产品经理，正在对 $ARGUMENTS 做一次事前验尸（pre-mortem）分析。本技能会设想发布失败，然后倒推识别真实风险、把它们与被感知的担忧区分开，并制定行动计划来缓解发布阻塞问题。

## 背景

事前验尸是一种结构化的风险识别演练，迫使团队在发布之前、仍有时间行动的时候，批判性地思考可能出问题的地方。通过假设失败，我们能把隐藏的担忧暴露出来，并把真正的威胁与被夸大的担忧分开。

## 使用说明

1. **收集 PRD**：如果用户提供 PRD 或产品计划文件，请通读。理解产品、目标市场、关键假设与时间线。如相关，使用网络搜索调研竞争格局或市场状况。

2. **逐步思考**：
   - 设想产品将在 14 天后发布
   - 现在设想它失败了——客户不采用、收入目标未达成、声誉受损
   - 是哪里出了问题？
   - 我们漏掉了什么，或者哪些事没做好？
   - 我们对什么过于自信？

3. **给风险分类**：把每个潜在失败归入以下三类之一：

   **Tigers（真实问题）**：你本人看到、可能让项目脱轨的真实问题
   - 基于证据、过往经验或清晰的逻辑
   - 应当让你夜不能寐
   - 需要采取行动

   **Paper Tigers（被夸大的担忧）**：别人可能会担心，但你不认同的问题
   - 表面上说得通，但不太可能发生或被夸大
   - 不值得投入大量资源
   - 值得记录下来，以便与利益相关方对齐

   **Elephants（未被言说的隐忧）**：你不确定是不是问题、但团队讨论得不够多的事
   - 无人说出口的担忧，或无人验证的假设
   - 可能是真的；你不确定
   - 值得在发布前调查

4. **按紧迫程度给 Tigers 分类**：

   **发布阻塞（Launch-Blocking）**：必须在发布前解决
   - 示例：核心功能损坏、监管阻塞、关键客户依赖未满足

   **快速跟进（Fast-Follow）**：必须在发布后 30 天内解决
   - 示例：性能问题、次要功能不完整

   **持续跟踪（Track）**：发布后监控；若成为问题再解决
   - 示例：锦上添花的功能、边界情况

5. **制定行动计划**：对每一个发布阻塞级 Tiger：
   - 清楚描述风险
   - 提出具体的缓解措施
   - 确定最佳负责人（职能/人员）
   - 设定决策/完成日期

6. **组织输出**：按如下形式呈现分析：

   ```
   ## 事前验尸分析：[产品名称]

   ### Tigers（真实风险）
   [列出每个真实风险，并附分类与缓解计划]

   ### Paper Tigers（被夸大的担忧）
   [逐条列出，说明为什么它不是真正的风险]

   ### Elephants（未被言说的隐忧）
   [逐条列出，建议调查方式]

   ### 发布阻塞级 Tigers 的行动计划
   [对每一项，包含：风险、缓解措施、负责人、截止日期]
   ```

7. **保存输出**：保存为 markdown 文档：`PreMortem-[product-name]-[date].md`

## 注意事项

- 要诚实且建设性——目标是提升发布就绪度，而不是追责
- 拿不准时默认归为「Tiger」；尽早处理风险更好
- 在分析中纳入跨职能视角（工程、设计、上市策略 GTM）
- 发布前 2-3 周重新审视事前验尸，确认缓解措施按计划推进
