# /test-scenarios —— 测试场景生成器

把用户故事或功能描述转化为 QA 可以立即执行的完整测试场景，覆盖正常路径、边界情况、错误处理以及跨浏览器/设备的考量。

## 调用方式

```
/test-scenarios [paste user stories or acceptance criteria]
/test-scenarios [upload a PRD or feature spec]
/test-scenarios User can reset their password via email link
```

## 工作流程

### 第 1 步：接收输入

接受：用户故事、验收标准、PRD 章节、功能描述，或任何描述预期行为的规格说明。

### 第 2 步：生成测试场景

应用 **test-scenarios** 技能：

为每个用户故事或需求生成：

**正常路径场景**：预期的用户流程正常运作
**边界情况**：边界条件、异常输入、并发操作
**错误场景**：出现问题时会发生什么
**安全场景**：如适用（身份认证、权限、数据访问）
**性能场景**：如适用（负载、超时、大数据量）

### 第 3 步：组织输出

```
## 测试场景：[功能]

**来源**：[用户故事 / PRD / 描述]
**场景总数**：[数量]
**覆盖**：[正常路径 / 边界情况 / 错误 / 安全 / 性能]

### 场景 1：[标题]
**测试对象**：[哪个故事或需求]
**前置条件**：[所需准备]
**用户角色**：[由谁执行]

| 步骤 | 操作 | 预期结果 |
|------|--------|----------------|
| 1 | [用户操作] | [预期的系统响应] |
| 2 | [用户操作] | [预期的系统响应] |

**后置条件**：[完成后的状态]
**优先级**：[严重 / 高 / 中 / 低]

---
[每个场景重复以上结构]

### 覆盖矩阵
| 需求 | 正常路径 | 边界情况 | 错误处理 | 备注 |
|------------|-----------|-----------|---------------|-------|

### 测试数据需求
[执行这些场景需要哪些测试数据]
```

保存为 markdown。

### 第 4 步：提供后续步骤

- 「要我 **为这些场景生成测试数据** 吗？」
- 「要不要为某个特定场景 **补充更多边界情况**？」
- 「要我 **创建这些场景所测试的用户故事** 吗？」

## 说明

- 先覆盖正常路径，再逐层加入边界情况 — 确保基本流程可用后再测试边界
- 原始故事中的每条验收标准都应至少映射到一个测试场景
- 同时包含正向测试（它能正常工作）和负向测试（它能优雅地失败）
- 对 API 而言，需包含限流、超时、格式错误的请求和认证失败等场景
- 标出需要特定测试环境或第三方服务 mock 的场景
