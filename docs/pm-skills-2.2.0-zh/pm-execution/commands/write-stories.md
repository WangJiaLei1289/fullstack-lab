# /write-stories —— 待办项生成器

把一个功能拆解为结构良好的待办项。按团队的偏好从三种格式中选择，每种都包含完整的验收标准。

## 调用方式

```
/write-stories user Allow users to export reports as PDF and CSV
/write-stories job Notification system for task deadlines
/write-stories wwa Dark mode for the mobile app
/write-stories [upload a PRD or feature spec]      # 询问格式偏好
/write-stories                                      # 询问功能与格式
```

## 格式

### 用户故事
**格式**：「作为 [用户类型]，我希望 [能力]，以便 [收益]」
应用 **user-stories** 技能：
- 遵循 3C 原则：Card（卡片）、Conversation（对话）、Confirmation（确认）
- 用 INVEST 准则校验：Independent、Negotiable、Valuable、Estimable、Small、Testable
- 在相关处包含设计链接或原型引用

### 任务故事
**格式**：「当 [情境] 时，我希望 [动机]，以便 [结果]」
应用 **job-stories** 技能：
- 关注情境与上下文，而不是用户角色
- 扎根于研究中观察到的真实用户场景
- 适合以 JTBD 为导向的团队

### WWA（Why-What-Acceptance）
**格式**：Why [战略背景] → What [交付物] → Acceptance [标准]
应用 **wwas** 技能：
- 包含战略推理（我们为什么要做这件事）
- 产出独立、有价值、可测试的待办项
- 适合需要业务背景的跨职能团队

## 工作流程

### 第 1 步：接收功能

以任何形式接受：PRD、功能描述、用户研究发现或口头想法。如果提供了 PRD，提取需求以便拆解。

### 第 2 步：确定格式

如果调用时未指定，就询问：
- 「你们团队用哪种格式？**用户故事**、**任务故事** 还是 **WWA**？」
- 如果不确定，推荐默认使用用户故事

### 第 3 步：拆解功能

- 把功能拆成 5-15 个独立故事（小到能在一个冲刺内完成）
- 确保每个故事独立有价值（自身就能交付用户价值）
- 按依赖关系和优先级排序
- 为每个故事写 3-5 条验收标准
- 标出需要设计输入或技术预研（spike）的故事

### 第 4 步：生成故事

```
## 待办列表：[功能名称]

**格式**：[用户故事 / 任务故事 / WWA]
**故事总数**：[数量]
**预估总工作量**：[如可能]

### 故事

#### 故事 1：[简短标题]
**[按所选格式撰写的故事]**

验收标准：
- [ ] [标准 1]
- [ ] [标准 2]
- [ ] [标准 3]

优先级：[P0/P1/P2] | 工作量：[S/M/L] | 依赖项：[无或列出]

---
[每个故事重复以上结构]

### 故事地图
[可视化排序：必须有 → 应该有 → 可以有]

### 技术说明
[横切关注点：API 变更、数据迁移、基础设施]

### 未决问题
[开始实现前需要答案的事项]
```

保存为 markdown。

### 第 5 步：提供后续步骤

- 「要我 **为这些故事生成测试场景** 吗？」
- 「要我 **为开发和测试创建假数据** 吗？」
- 「要我 **估算这些故事的冲刺产能** 吗？」
- 「要我 **转换成另一种格式**（用户故事 ↔ 任务故事 ↔ WWA）吗？」

## 说明

- 一个故事 = 一个可独立交付的价值单元 — 如果它需要另一个故事才有用，就应该合并
- 验收标准应让 QA 无需额外解读即可测试
- 错误处理和边界情况值得拥有各自的故事，而不是塞进正常路径故事的要点里
- 如果功能较大（15 个以上故事），建议归入史诗或阶段
- 标出任何需要 spike 的故事（在可估算之前需要先做技术调研）
