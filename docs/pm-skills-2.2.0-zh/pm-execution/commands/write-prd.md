# /write-prd —— 产品需求文档

创建一份精简的 PRD，用于对齐利益相关方并指导开发。可以接受从模糊想法到详细简报的任何输入。

## 调用方式

```
/write-prd SSO support for enterprise customers
/write-prd Users are dropping off during onboarding — we need to fix step 3
/write-prd [upload a brief, research doc, or strategy deck]
```

## 工作流程

### 第 1 步：理解功能

以任何形式接受输入：
- 功能名称（「SSO 支持」）
- 问题陈述（「企业客户一直在要求集中式身份认证」）
- 用户请求（「用户希望把数据导出为 CSV」）
- 模糊想法（「我们应该处理一下新手引导流失问题」）
- 上传的文档（简报、调研、Slack 讨论串、邮件）

### 第 2 步：只补关键的信息缺口

提取输入已经提供的信息，通过调研回答网络能查到的问题（既有方案、竞品、市场背景），而不是直接提问。如果以下三项中有缺失，在动笔前一次性询问，最多问三个问题：

1. **用户问题**：这解决什么问题？谁会遇到，痛点有多强？
2. **目标用户**：面向哪些用户细分？他们目前用什么变通方案？
3. **成功指标**：我们如何判断这件事奏效？如果做好了，哪个指标会变化？

约束条件、既有方案和范围偏好只有用户想要详细版本时才值得询问。如果用户说「直接写吧」，那就照做，并把缺口标记为假设。

### 第 3 步：生成 PRD

应用 **create-prd** 技能：使用其 8 段式模板，默认保持精简（约一到两页）。只有用户要求时才写详细版本。文档开头为：

```
## 产品需求文档：[功能名称]

**作者**：[用户]
**日期**：[今天]
**状态**：草稿
```

然后是八个部分：摘要、联系人（如已知）、背景、目标、细分市场、价值主张、解决方案、发布。细分市场和价值主张始终包含；每个价值主张使用 6 部分模板（Who、Why、What before、How、What after、Alternatives）。在「发布」部分写明第一版不会做什么，在「解决方案 → 假设与未决问题」中写明仍然未知的内容。

### 第 4 步：评审并迭代

生成后，用一句话说明你刻意省略了什么，然后提供：
- 「要 **详细版本** 吗，还是由我展开某个特定部分？」
- 「要我 **进一步收紧范围** 吗？我可以质疑第一版真正需要包含什么。」
- 「要我 **对这份 PRD 做一次事前验尸** 吗？」
- 「要我 **把它拆成用户故事** 交给工程吗？」
- 「要我 **创建一份利益相关方更新** 来同步这件事吗？」

将 PRD 保存为 markdown 文件到用户的工作区。

## 说明

- 在范围上要有主见 — 一份紧凑的 PRD 好过一份空泛含糊的 PRD
- 如果想法太大，主动建议分阶段，只写第 1 阶段的规格
- 非目标与目标同等重要 — 它们能防止范围蔓延
- 成功指标必须具体：「提升 NPS」不好，「在发布后 90 天内把 NPS 从 32 提升到 45」才好
- 未决问题应确实尚未解决 — 不要列出你能从上下文回答的内容
- 如果用户提供了调研材料，把洞察融入背景部分并注明出处
