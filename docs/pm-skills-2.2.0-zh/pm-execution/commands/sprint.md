# /sprint —— 冲刺生命周期

覆盖冲刺生命周期的三种模式：**plan** 用于冲刺规划，**retro** 用于复盘，**release-notes** 用于交付沟通。

## 调用方式

```
/sprint plan 2-week sprint, 4 engineers, focus on checkout improvements
/sprint retro [paste team feedback or sprint data]
/sprint release-notes [paste tickets, changelog, or PRD]
/sprint                    # 询问你处于哪个阶段
```

## 模式

---

### Plan 模式

为冲刺规划做准备：产能估算、故事选取和风险识别。

#### 工作流程

**第 1 步：收集冲刺上下文**
- 冲刺周期（1 或 2 周）
- 团队构成（工程师、设计师、QA — 以及可用性）
- 冲刺目标或重点领域
- 待考虑的待办项（粘贴、上传或描述）
- 上个冲刺遗留下来的事项
- 已知的干扰（假期、值班、会议）

**第 2 步：估算产能**

应用 **sprint-plan** 技能：

- 扣除会议、值班、休假后，计算可用的工程小时/点数
- 基于历史数据（如提供）或行业标准（理论产能的 70%）做速率调整
- 展示每位成员的产能明细

**第 3 步：选取并排序故事**

- 推荐适合产能的故事
- 标出依赖链（A 必须在 B 开始前完成）
- 识别风险：规格不完整的故事、有外部依赖的故事，或需要设计输入的故事
- 平衡快赢项与较大的事项
- 确保每个故事都有验收标准

**第 4 步：生成冲刺计划**

```
## 冲刺计划：[冲刺名称/编号]

**周期**：[日期]
**冲刺目标**：[一句话]
**团队**：[成员及可用性]

### 产能
| 成员 | 可用天数 | 点数/小时数 | 备注 |
|--------|--------------|-------------|-------|

**总产能**：[X] 点/小时
**建议承诺量**：[Y] 点/小时（含缓冲）

### 选中的故事
| # | 故事 | 点数 | 负责人 | 依赖项 | 风险 |
|---|-------|--------|-------|-------------|------|

### 冲刺风险
1. [风险] — 缓解措施：[行动]

### 完成定义
- [ ] 代码已评审
- [ ] 测试通过
- [ ] 已部署到预发环境
- [ ] QA 已验收
- [ ] 文档已更新（如适用）
```

### Retro 模式

引导一场结构化的复盘，产出可落地的改进。

#### 工作流程

**第 1 步：收集冲刺反馈**

接受以下输入：
- 团队反馈（从问卷、Slack 或协作文档中粘贴）
- 冲刺指标（速率、缺陷、事故）
- 用户自己的观察

询问：「你偏好哪种复盘形式？」
- **Start/Stop/Continue**（简单、快速）
- **4Ls**（Liked、Learned、Lacked、Longed for）
- **帆船（Sailboat）**（风 = 助力，锚 = 拖慢，礁石 = 风险，岛屿 = 目标）

**第 2 步：分析并结构化**

应用 **retro** 技能：

- 把反馈归入所选框架
- 识别主题与模式
- 区分症状与根因
- 突出值得庆祝的成果

**第 3 步：生成复盘总结**

```
## 冲刺复盘：[冲刺名称]

**日期**：[今天]
**形式**：[Start/Stop/Continue | 4Ls | 帆船]
**参与者**：[如已知]

### 进展顺利的部分
[按主题分组并附支撑证据]

### 不顺利的部分
[按主题分组并附根因分析]

### 关键洞察
[浮现出的 2-3 个模式]

### 行动项
| # | 行动 | 负责人 | 截止日期 | 优先级 |
|---|--------|-------|----------|----------|

### 本冲刺指标
| 指标 | 本冲刺 | 上冲刺 | 趋势 |
|--------|-----------|------------|-------|
```

### Release Notes 模式

从技术产物生成面向用户的发布说明。

#### 工作流程

**第 1 步：接收发布内容**

接受：
- Jira/Linear 工单或变更日志
- PRD 或功能规格
- Git 提交信息或 PR 描述
- 团队内部的交付内容摘要

**第 2 步：转换**

应用 **release-notes** 技能：

- 把技术语言转化为用户收益
- 分类为：新功能、改进、缺陷修复
- 用产品的声音来写（如不明确，先询问语气偏好）
- 把影响最大的变更放在最前面

**第 3 步：生成发布说明**

```
## 新内容 — [版本/日期]

### 亮点
[用 1-2 句话概述最重要的变更]

### 新功能
- **[功能名称]** — [用平实语言说明的用户收益]

### 改进
- **[改进项]** — [现在哪里更好了]

### 缺陷修复
- 修复了导致 [用户影响] 的 [问题]

### 即将推出
[下个版本的可选预告]
```

保存为 markdown，并提出可为不同渠道调整格式（博客文章、应用内、邮件、Slack 公告）。

## 说明

- 对 plan 模式：为计划外工作预留 20% 缓冲 — 按 100% 产能规划的团队总是失败
- 对 retro 模式：聚焦 2-3 个高影响行动项，而不是 10 件没人会做的事
- 对 release notes：始终把变更表述为用户收益，而非技术实现
- 各模式可以互相衔接：plan →（冲刺进行）→ retro → release-notes
