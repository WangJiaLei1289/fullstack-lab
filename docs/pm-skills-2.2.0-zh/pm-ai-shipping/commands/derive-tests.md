# /derive-tests —— 把意图转化为测试

文档说的是系统 *应该* 做什么。审计发现的是代码 *没有* 做到的地方。而测试，正是防止这个差距在下一轮 AI 修改之后重新裂开的东西。这个命令读取文档化的意图，把每条承重规则变成一个具体的测试用例，把它们分门别类：哪些要自动化、哪些需要受保护的真机运行、哪些保持手工——然后推荐一个能让 `main` 保持诚实的门禁：仓库自身说明里定义的那个；如果没定义，就是一个合并前必须变绿的 CI 门禁。

这个命令产出的是覆盖图（`tests.md`）和具体测试用例，而不是一个完成的测试套件——确定性的用例由你或下一个 agent 来实现。如果仓库已经维护了测试覆盖文件（无论叫什么名字），那个文件就是覆盖图：更新它，而不是另起一份（见 **shipping-artifacts** 技能的 *Locations and names* 规则）。

## 调用方式

```
/derive-tests
/derive-tests the checkout flow
/derive-tests supabase/functions
/derive-tests check
/derive-tests check the checkout flow
```

第一个参数为 `check` 时，会在其后的范围上运行**仅检查模式**（见下文），而不是执行工作流程。

## 前置条件：文档化的意图

测试是从文档推导出来的，所以文档必须先有。如果系统文档（位于仓库的文档位置，默认是 `documentation/`）缺失或内容单薄，请先运行 `/document-app`（`/derive-tests` 会重点读取 `flows.md`、`permissions.md` 和 `automation.md`）。你无法为从未写下的规则建立覆盖映射——意图缺失时，直接说明，而不是编造规则来测试。

## 工作流程

### 1. 读取意图，以及已经存在的测试

读取适用的系统文档（架构、流程、权限、变量，以及存在的 emails、cron、seo、automation 文档）。采用 **shipping-artifacts** 技能来明确每份文档该包含什么，采用 **intended-vs-implemented** 技能的纪律：把文档当作待验证的说法，而不是证据。

然后盘点**现有测试套件**——测试文件、它们实际断言了什么、今天在 CI 里运行的是什么。你产出的覆盖图必须区分 *现在* 已有的覆盖和你 *建议* 的覆盖；跳过这一步会得到一张虚假的绿色覆盖图，声称规则已被钉住，而实际上没有任何检查。如果没有测试，就直说——这本身就是一个发现。

### 2. 提取值得测试的规则

挑出承重的（load-bearing）、确定性的规则——即违反后会跨越信任、数据、资金、租户或隐私边界的那些：

- 授权允许**与拒绝**两类用例（尤其是 `flows.md` 中的边界穿越和 `permissions.md` 中的矩阵），
- 每个数据汇聚点上的输入校验和输出编码，
- 任务和去重键的幂等性，
- 失败即拒绝（fail-closed）的默认行为（错误 / 超时 / 缓存未命中 / 开关路径必须拒绝，而不是允许），
- 副作用触发条件（邮件究竟何时发送、写入何时提交、付费动作何时触发），
- 公开或机器人路由上「仅公开数据」的约束，
- `automation.md` 中任何 agent 的输出契约和工具面限制。

跳过表面行为。一条规则只有在做错时会伤害行动者以外的人时，才值得为它写测试。

### 3. 构建覆盖图

每个用例一行：**规则 → 预期行为（含反例）→ 证据来源（文档 + 代码）→ 测试类型 → 状态（existing / proposed / none）**。状态列是让覆盖图保持诚实的关键——只有当仓库中确实有一个测试在今天断言了某条规则时，才把该规则标为 *existing*。

测试类型：

- **unit（单元测试）**——纯函数、确定性，不依赖外部服务。
- **integration（确定性集成测试）**——针对本地或内存中的依赖（测试数据库、模拟的服务商）运行真实接线，并且每次运行结果一致。
- **guarded live（受保护的真机测试）**——需要真实的外部数据库、邮件服务商、LLM 或第三方。只在显式开关之后运行，绝不进入默认门禁。
- **manual（手工测试）**——UI/视觉或需要人工判断的部分。属于评审清单条目，不是自动化测试。

**门禁必须要求什么**（托管 CI，或仓库实际使用的任何门禁）：确定性的本地集合——单元测试加确定性集成测试，即在没有任何真实依赖时每次运行结果都相同的那些测试。决策逻辑可以隔离时优先用 **unit**；当规则存在于接线层（中间件、RLS、授权守卫）而只有真实但本地的依赖才能验证时，才用 **integration**。guarded-live 和 manual 行永远不进入默认运行的门禁。

当某条规则只能真机验证时，你可以把它的 *决策* 抽成一个纯 helper，让逻辑可以被单元测试——但这只能作为测试真实执行路径的**补充，而不是替代**。单元测试证明的是 helper 的逻辑；它**不能**证明框架真的调用了它。接线与策略执行（路由中间件、数据库行级安全、授权守卫、服务商配置）仍然需要集成测试或 guarded-live 检查，否则 helper 就会变成一道策略影子：测试通过，而真实路径毫无保护。

### 4. 提出测试

对每条能用确定性自动化测试（unit 或 integration）钉住的规则，写出用例：名称、arrange/act/assert 意图，以及它必须拒绝的反例。按用例所守护的文档或流程分组。优先写能钉住该规则的最小测试——针对一个边界的一条清晰断言，胜过因十个原因失败的庞大集成测试。

### 5. 推荐门禁

从仓库声明的门禁策略出发。它的 agent 指令、贡献指南或发布文档可能已经写明什么能门禁合并或发布——本地命令加人工确认、托管 CI 工作流，或别的形式。如果有，那个策略就是门禁：把它连同出处记录到覆盖图里，确认确定性集合在其中运行，不要在其之上再推荐托管 CI 或分支保护。如果确定性集合不在那个门禁里运行，就把它作为一条发现报告给负责人，而不是提议换一个门禁。

仓库没有声明任何策略时，推荐（而不是悄悄安装）一套与仓库技术栈和现有工具匹配的 CI 配置：

- 在**每个 pull request 上运行确定性本地集合**（单元测试 + 任何不需要真实服务的集成测试），
- 让 **guarded-live 测试保持按需启用**（手工或定时，永不阻塞），
- **要求合并到 `main` 时状态为绿**：通过必需状态检查 + 分支保护。

把工作流文件和分支保护设置作为明确标注的建议输出，由用户批准，而不是直接应用变更。

### 6. 报告覆盖与空白

把 `tests.md` 写成三个清晰分开的部分：

- **现有覆盖**——仓库中的测试 *今天* 就已经钉住的规则（来自第 1 步的盘点）。
- **建议的测试**——你推荐但尚不存在的用例，按类型分组。
- **空白**——有文档但**完全没有验证**的规则，按越过它们会暴露什么来排序。

这些空白就是待办积压，也正是下一轮 AI 修改可能悄悄破坏边界的地方。要如实说明「建议」≠「现有」：一条规则只有在测试真正断言它之后才算被覆盖。

## 仅检查模式

适用于覆盖图由人手工维护、或由执行门禁的人维护的仓库，这样一次发布就能确认覆盖图是最新的，而不必让这个命令重写它。**不写任何文件**：不写覆盖图，不写报告。只读测试，不运行测试。文档单薄时不要运行 `/document-app`，把它们列在 *未检查* 下。

1. 按工作流程的方式找到覆盖图（见 **shipping-artifacts** 技能的 *Locations and names* 规则）。如果没有，说明并停止。
2. 逐行与系统文档和测试套件比对。以下情况即为过时：
   - 有文档的规则没有对应行，或某行引用的规则文档已不再这样陈述、或已改述；
   - 标为 existing 的行提到的测试已不存在，或该测试并未断言这条规则；
   - 某个测试钉住了一条在覆盖图中标为 proposed 或 none 的规则；
   - 引用的路径、测试名或门禁命令已与代码树不符。
3. 不要判断哪一侧错了。覆盖图可能落后，或者文档、测试已经从覆盖图记录的状态漂移；这由负责人决定。

输出，打印在对话中：

```
覆盖检查：[scope] — 仅检查，未写任何文件

### 过时条目
1. [规则或行]
   - 覆盖图称：[条目] — `[覆盖图路径]:[行号]`
   - 文档或测试称：[它们陈述或断言的内容] — `[路径]:[行号]`
   - 负责人决定：修改覆盖图、文档或测试。

### 未检查
- [文档单薄或缺失、无法读取断言的测试、范围之外的部分]

### 总结
覆盖检查，[日期]，提交 [短 SHA]，范围 [scope]：读取 [N] 行覆盖图，[N] 条过时条目，[N] 项未检查。只读测试，未运行。未写任何文件。修哪一侧由负责人决定。
```

如果 *过时条目* 一节为空，要说明读了多少内容才得出这个结论。然后停止：不要主动提出重写覆盖图。

## 输出

```
测试覆盖：[scope]

| 用例 | 规则（文档） | 预期行为（含拒绝用例） | 证据 | 类型 | 状态 |
|------|------------|----------------------|------|------|------|
[status: existing / proposed / none]

### 现有覆盖
[仓库中已有的测试，每个都对应它所钉住的规则]

### 建议的测试
[按流程/文档分组 — 名称 · 断言 · 反例 · 类型]

### 门禁
[仓库声明的门禁策略及其出处，以及确定性集合是否在其中运行——若未声明，则给出针对所检测技术栈的工作流片段 + 「合并前必须变绿」的分支保护说明]

### 空白——有文档但未验证
[尚无测试的规则，按越过它们会暴露什么排序]
```

把覆盖图写入仓库已有的覆盖文件；如果没有，写入 `documentation/tests.md`。把完整报告写入仓库的报告位置；如果没有，写入 `reports/test_plan_{timestamp}.md`。把两个路径都告诉用户，并说明哪些是插件的默认值。

## 注意事项

- 这是「文档 == 实现」的验证半边：审计发现今天的差距，这些测试阻止它明天重新出现。
- 不要为了造出覆盖率而编造规则。如果文档沉默，缺口在文档本身——先修 `/document-app`。
- 无论门禁是什么，都不要把外部服务接进默认门禁运行；不稳定的真机测试会侵蚀门禁，直到人们开始无视它。
- 只覆盖测试推导。差距审计本身用 `/security-audit-static`；完整的 文档 → 审计 → 测试 → 交付包 流程用 `/ship-check`。
