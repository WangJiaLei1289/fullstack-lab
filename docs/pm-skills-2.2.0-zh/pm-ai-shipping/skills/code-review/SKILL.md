# 代码评审

## 目的

大多数评审输出都是噪音：一长串*看起来*有问题的事项，没有排优先级、没有被反驳，也无法据以行动。本技能产出的恰恰相反——少量发现项，每项都带有一个必需行为、一个可行的触发方式、一处具体的矛盾、一个可观察的后果，以及已经核查过的最强反论。

它的核心判断是：**评审者漏掉的缺陷，很少能在单个文件内看见。** 它们是两个参与方之间的分歧，而这两方单独看时都显得合理——一个调用方与一个被调方、一个生产者与一个消费者、一个写入者与一个之后的读取者、两个本应建立相同状态的分支。逐文件套用的检查清单看不到这些，因为两半从不同时出现在视野里。所以这里的评审单元是**约定**，而不是文件。

## 结构：一套引擎，三个锚点

代码评审就是本技能。**正确性是它的核心**——这是通用工具覆盖得最差的维度，也是下面完整展开的维度。**性能与安全是子场景**：同一套引擎、同样的反驳纪律、同样的报告契约，只是锚点不同，各自再加一两条规则。

| 子场景 | 锚点 | 规则所在位置 |
|---|---|---|
| **正确性**（*核心、默认*） | 跨边界的参与方之间的约定 | 本文件 + `references/correctness-taxonomy.md` |
| **性能** | 工作负载 → 资源需求 → 增长或争用 → 实质后果 | `references/performance-review.md` |
| **安全** | 来源 → 信任边界 → 汇聚点（sink），且有攻击者控制来源 | `references/security-review.md` |

只在该子场景被选中时才读它的文件。每份文件都刻意很短：它只说明*有什么不同*，本文件其余内容依然适用。

子场景是各自独立*激活*的，而不是互斥的。一个根因可能同时带来正确性和安全影响——只报告一次，把两方面影响都写上。

## 调用方式

```
/pm-ai-shipping:code-review
/pm-ai-shipping:code-review dimensions=correctness scope=changes
/pm-ai-shipping:code-review dimensions=performance,security
/pm-ai-shipping:code-review dimensions=all
```

Claude Code 自带一个 `/code-review`。当你要用的是本技能时，请使用上面带插件前缀的形式。

这些是指令参数，不是 shell 标志。

- **默认：`correctness`。** 只说「评审一下」或「找找缺陷」，就意味着只做正确性。
- 显式列表则精确选中那些子场景；`all` 选中三个。绝不要静默地重新解释一个未知的或空的选择——要问。
- **范围：** 按被要求的内容来。否则优先评审工作区改动（若存在），再否则评审整个仓库。
- **在开始调查之前，先说明所选维度、范围和比较基线。**
- 评审改动意味着沿着依赖*越过*被改动的行，并区分改动**引入**的缺陷与改动仅仅**暴露**的缺陷。
- 只评审并报告。只有被要求时才应用修复。

## 共享引擎

每个子场景都用同一副骨架。只有锚点和反驳规则不同。

**梳理一条流程 → 识别一项义务 → 检查每个参与方 → 构造一次违反性执行 → 追踪后果 → 尝试反驳 → 报告。**

先构建一张最小地图：输入、主要执行流程、谁拥有哪部分状态、外部依赖、可观察的效果。每个被选中的子场景都会丰富它——不要建三张地图，也不要让只做安全维度的评审去等正确性地图。

## 正确性：约定引擎

*边界*是语义上的，不是文件切分。它分隔调用方与被调方、两个回调、同一函数的两次执行、生产者与消费者，或者一个现在写入、之后才被读取的值。

对于每一项有后果的约定，在工作笔记里记下以下内容——不是写进报告：

```
参与方：
交换的值、实体或效果：
权威源（谁决定真正的答案）：
标识与生命周期 / 版本：
必需的关系：
支撑该关系的证据：
相关的状态转换或顺序：
可观察的消费者或后果：
```

**在不臆造意图的前提下确立义务。** 证据来自规格说明、有文档的契约、语言或协议语义、编码了期望的测试，或者必然存在的生产者/消费者关系。仅凭消费者的实现不能证明消费者是对的。当参与方存在分歧时，要说明这个分歧为何会产生*错误结果*——有时矛盾是确定的，而该改哪一侧则确实待定。缺少文档是一种局限，不自动等同于一条发现项。

**从约定最可能出问题的地方开始：** 被转换或协商的值、被重新分配的标识、变成异步的工作、被持久化再重新加载的状态、多个必须彼此一致的效果。然后对普通决策、算术、边界和错误分支做一遍本地检查——锚点不能变成一个筛掉普通缺陷的过滤器。

### 强制构造一次违反性执行

在构造出打破它的执行之前，怀疑不算发现项。在实现允许的地方：

- 让**被请求的**值与**被接受或实际生效的**值不同；
- 让两个操作同时存活，并改变它们的完成顺序；
- 在观察与使用之间改变相关的标识或世代；
- 比较本应最终进入等价状态的不同转换；
- 在效果之间注入失败，并在完成前注入中断；
- 试跑空输入、正好在边界上的输入和紧邻边界的输入。

确认每个用例确实可达。不要假设。

### 两个必须强制探测、不能只提一句的透镜

在对真实代码库中植入的运行时缺陷所做的大规模评估中，有两类几乎从未被强力的智能体*报告*过——不是修的时候漏了，是看的时候就没看到。把它们写进检查清单也没用；每一类都需要一次显式探测：

1. **权威源对账（authority reconciliation）。** 沿着一个提议值穿过校验、规范化、协商或提交，找出仍然由**提议**推导而来的下游状态，而权威源可能返回不同的东西。*被请求的值不是被应用的值。* 探测方式：强行让两者分离，然后问还有谁在读那个请求值。
2. **标识与关联。** 追踪一个操作的结果如何找到它归属的实体，然后确认该关联键在重叠、重排、移除和复用的情况下，能足够久地保持唯一、稳定且有效。一个标签、一个位置或到达顺序之所以可疑，恰恰是因为这些性质可能不成立。探测方式：并发运行两个操作，并让它们乱序完成。

完整的一套十三种诊断透镜，每一种都带有检测线索，见 `references/correctness-taxonomy.md`。它们是相互重叠的透镜，不是要凑满的配额。

## 反驳：让这件事值得做的纪律

一个候选缺陷只有同时具备以下五项，才成为一条发现项：

1. **有支撑的义务**——必须成立的是什么，依据是什么证据。
2. **可行的执行**——真实系统允许的输入、状态和顺序。
3. **具体的矛盾**——义务在哪里失效。
4. **可观察的后果**——错误的输出、状态、效果、完成情况或进度。
5. **已审查的反论**——那种最强的、本可阻止或修复它的机制。

要主动去寻找反驳：一个使该执行不可能的包围性保证；排除该交错执行的同步；在任何有后果的读取之前的对账；一项有意为之的契约；排除该输入的前置条件；由另一个所有者负责。

| 结论 | 规则 |
|---|---|
| **保留** | 证据确立了缺陷；已核查的反论无法阻止它。 |
| **丢弃** | 所引证据击破了执行、义务或后果。 |
| **未决** | 某项关键契约或运行时事实未知。将其*与发现项分开*列出。 |

不要把安全子场景的攻击者/受害者检验搬进正确性。**一个正确性缺陷可以只伤害触发它的人，却依然严重。** 同样地，「除非被证伪否则保留」在这里过于宽松——一个没有构造出执行的、无根据的怀疑不是发现项。当两个子场景都激活时，只把各自的检验用于各自的维度。

**吸收不是阻止。** 最昂贵的反驳错误，是发现下游有某个东西恰好掩盖了缺陷——一个通常存着该值的缓存、一次通常成功的重试、一个通常正确的默认值——然后就把发现项丢掉了。那不是保证，那是胜算不错的巧合，而且会在吸收者变冷、被逐出或被重新配置的那天失效。只有在某个机制使该执行*不可能*时才丢弃，并说明是哪个机制。同样的道理，**「几乎总是能跑通」描述的是竞态，而不是反驳**——一个通常能正确收敛的时间窗口就是一条发现项，而你必须去推理哪一侧通常获胜这个事实，本身就是证据。

通过的测试、不熟悉的代码、可疑的命名、缺失的测试，以及与同类实现的差异，都是值得调查的证据——它们都不是证明，也都不是反驳。按被违反的约定和根因去重，绝不按文件去重。没有发现项配额；零条有支撑的发现项是有效结果。

## 并行

按**完整流程或相互关联的约定组**分工——绝不按文件分，也绝不按分类法类别一人一个。按文件切分恰恰是会掩盖跨边界缺陷的那种分法，而跨边界缺陷才是有价值找的东西。

1. 协调者构建初始地图并识别共享状态。
2. 每个工作者拿到一段有边界的流程、它的参与方、所选子场景和待解问题。
3. 工作者检查其约定的**两侧**，并可以跟踪清单之外的依赖。
4. 工作者返回候选、引用的证据、已完成的反驳和未解决的关系。
5. 协调者对齐各项假设，以及任何跨越分工的关系。
6. 强候选在报告前另做一轮验证。

**允许重叠读取。** 两个工作者读同一个权威源，远比各自只握有契约的一半便宜。留出整合余力：一个横跨两项分工的未解决关系，在有人把它闭合之前会一直处于未检查状态。目标是单层分工；如果无法委派或范围很小，就按同样流程串行执行。

**让工作者使用可用的最强模型，并与当前会话的投入档位匹配。** 这是召回优先的工作：漏掉一条跨边界流程就是代价高昂的失败，而一个悄悄降级到更便宜的模型或更低投入档位的工作者，是丢掉它最省事的办法。如果有任何工作者被重路由或降级，在报告里说明是哪个——以为「一个模型看到了全部」的读者会误判覆盖范围。

**一个模型。在每个工作者上都写明它。** 这里的分工换来的是覆盖范围，而不是第二意见。每次派生时都显式传入协调者自己的模型——「继承」不是一个路由决策，而一个悄悄落到更便宜模型上的工作者，是丢掉一条发现项最容易的路径。**不要引入不同的模型**来做评审或交叉核对，除非被明确要求：混用模型会让结果无法归因；当本技能正在被测量或跨模型比较时，一个外来工作者会让那个数字失效。独立的第二模型复核是一个单独的、显式调用的步骤（`/ship-check` 第 6 步），绝不是本技能自己会去够的东西。

**告诉工作者：他们是在阅读，不是编辑。** 评审工作者需要读取、搜索和导航；它不得修改代码树。把这一点写进工作者的指令里——一个开始编辑的工作者会从评审漂移成「顺手」修复，并且不再报告它悄悄修好的东西，发现项也就无法再对照它们所描述的代码进行核查。要在提示词里说明，而不是假设宿主会强制执行；并在运行结束时确认代码树未被改动。

## 报告

先给有支撑的发现项，按影响排序。把严重程度与证据强度分开。

```
评审范围：
比较基线：
所选维度：

[严重程度] [维度] 具体后果
  期望：        必需的行为，以及支撑它的证据
  触发：        可行的前置条件与执行
  缺陷：        被违反的关系
  证据：        每个参与方的源码位置
  影响：        可观察的后果与受影响范围
  反驳：        已核查的最强反论，以及它为何不成立
  补救：        对被违反关系的最小修正
  验证：        实际执行了什么，与仅从源码确立的内容

覆盖情况：
未检查的领域与关键未知项：
```

**跨边界缺陷要同时引用两个参与方**，不要只按文件给发现项分组——那会掩盖评审存在的意义所在的关系。

**覆盖意味着做过的功，而不是勾过的框。** 对每个所选子场景都要报告：已检查且有支撑的发现项 · 已检查、无有支撑的发现项 · 不适用（附原因）· 未检查（附原因）。某个类别零发现**不**等于「未覆盖」，一张打勾的表格也不是完整性的证据。要说「在已检查范围内没有有支撑的发现项」——绝不要说这段代码没有缺陷。

## 备注

- 明确说出哪些地方做得好。一份只会指控的评审很容易被整体否定、不予采信。
- 这两个子场景背后都有成熟的命令：`/security-audit-static`（信任边界、汇聚点、OWASP 兜底）和 `/performance-audit-static`（过度获取、索引、缓存）。当子场景本身就是全部工作时，运行该命令；当它只是一次更广泛评审中的一个维度时，使用参考文件。本技能不再复述它们。
- 文档与代码这条轴使用 `intended-vs-implemented` 技能。
- 静态评审产出的是代码评审发现项，不是已确认的漏洞利用，也不是实测到的性能回退。
