# 子场景：性能评审

父引擎的一个特化。锚点变了；反驳纪律和报告契约不变。

**锚点：** 工作负载 → 资源需求 → 增长或争用 → 实质后果。

被检验的约定，存在于代码*对其工作负载的假设*与工作负载*实际会是什么样*之间。针对种子数据写的代码，认同的是一个在生产环境中不会存在的世界。这与任何其他失灵的约定形状相同：两个参与方，各自单独看都合理。

## 通用内核

与语言和栈无关。在应用任何技术专项检查清单之前先执行。

- **重复劳动**——扫描、解析、序列化、分配、初始化或 I/O 本该一次完成、提升到循环外或直接复用时，却又做了一遍。
- **增长关系**——资源使用如何随输入规模、并发度和经过时间缩放？这三者中任何一个出现超线性增长就是发现项；常数因子不是。
- **滞留**——队列、缓冲、缓存和集合在没有上界、淘汰策略或背压的情况下增长。无界滞留是一次延迟发作的失败。
- **复制与转换**——在热路径上于不同表示之间复制或转换数据，尤其是在两侧本可就同一种表示达成一致的边界处。
- **序列化与争用**——锁的持有时间和范围、单线程瓶颈、队头阻塞，以及把本不需要的工作留在临界区内。
- **放大**——重试、轮询、扇出和缓存未命中，把一个逻辑请求放大成许多真实请求。要在失败时检查倍率，而不是在成功时。

## 技术专项

只在底层技术确实存在时才应用——不要在一个没有数据库的程序里报告缺少数据库概念。对于数据支撑的应用（过度获取、`SELECT *`、缺少分页、索引定义、缓存层），`/performance-audit-static` 保有详细清单；使用它，而不是在这里复述。

## 什么样的东西算性能发现项

三项俱全，否则不是发现项：

1. **可达的工作负载**——输入规模、速率或并发度是系统实际会遇到的，从代码及其上下文确立，而不是假设。
2. **资源成本或增长关系**——消耗了什么，以及它如何缩放。
3. **实质后果**——用户能感受到的延迟、实际付出的成本、被触到的上限，或由此导致的失败。

## 反驳

针对真实的边界、摊销、复用、实际调用频率和有意的权衡去反驳。对一个上界硬性为四的集合做嵌套循环，不是发现项。在启动时只调用一次的代码里缺少缓存，不是发现项。

**区分实测与静态推断，并标明你做的是哪一种。** 绝不编造计时。绝不把缺少缓存、嵌套循环或缺少索引本身当作发现项——没有工作负载，那些只是观察，不是缺陷。
