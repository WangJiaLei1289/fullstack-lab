# 交付物：让 AI 编写的代码可评审的那套文档

## 目的

AI 智能体写代码很快，但它们不会留下关于*意图*的持久记录——系统本应做什么、谁被允许做什么、密钥存在哪里、哪些规则真的被验证过。没有这份记录，任何人（也没有任何审计智能体）都无法判断代码是否可以安全发布。本技能界定了那组能恢复可评审性的文档，数量不多。

这些文档写给两类读者：人类评审者和下一个 AI 编码智能体。它们是后续每一次审计的**意图状态**那一半——安全评审或性能评审的好坏，取决于它能拿来与代码作比较的意图有多好。

## 位置与命名：仓库自身的安排优先

本插件中的每个位置、文件名和文档格式约定都是**默认值**。宿主仓库自己的安排优先。在写任何东西之前（系统文档、覆盖图、审计报告），先找那套安排：

1. **智能体指令**——`AGENTS.md`、`CLAUDE.md`，以及它们导入或指向的内容。它们常常会写明文档放在哪个目录、目录里有哪些文件、每份由谁维护、日期怎么记录。
2. **文档位置**——一个已存在的 `docs/`、`documentation/` 或类似目录。
3. **已有的等价文件**——一份已经覆盖了下面某份文件所覆盖内容的文档，叫什么名字都行（`ARCHITECTURE.md`、`docs/security.md`、`docs/env.md`）。按它覆盖的内容来匹配，而不是按文件名。
4. **已有的测试覆盖图**——一份把行为映射到覆盖它的测试的文件，例如 `docs/test-coverage.md`。按它覆盖的内容来匹配：描述仓库如何测试的 `TESTS.md` 或 `testing.md` 是测试方法，不是覆盖图。
5. **报告位置**——仓库已经存放审计或评审输出的地方。

然后：

- **遵循你发现的东西。** 写进仓库的文档位置，更新它已有的等价文件而不是新建一份平行文件，并沿用它的命名与日期约定。每份文档必须包含的内容不变；变的只是它放在哪里、叫什么名字。如果它的智能体指令说明了文档如何维护或由谁维护，也照做。
- **只在仓库没有对应安排时使用插件的默认值：** 文档放在仓库根目录的 `documentation/` 下，文件名如下，覆盖图放在 `documentation/tests.md`，报告放在 `reports/<name>_{timestamp}.md`，不写「更新日期」行（文件历史才是权威来源）。
- **说明你用了哪一种。** 输出要写明每一个写入的位置和文件，以及各自遵循的是仓库安排还是插件默认值。
- **绝不要创建这样的文件：它的名字与已有文件只差字母大小写**——`tests.md` 与 `TESTS.md` 并列、`Architecture.md` 与 `architecture.md` 并列。在 Windows 和 macOS 上它们是同一个文件，所以写入会覆盖它；在其他系统上它们会变成两个文件，在下次检出时发生冲突。创建文件前先做大小写不敏感的检查。如果已有的那个覆盖的是同一件事，就用它。如果它覆盖的是别的事（一个描述测试方法的 `TESTS.md`，而不是覆盖图），不要写进它：改用仓库真正的等价文件；若没有等价文件，就挑一个不与任何东西冲突的名字。

在本插件中，`architecture.md` 或 `tests.md` 这样的名字指的*就是那份文档，无论在仓库里放在哪里、叫什么名字*。

## 这套文档如何组织

这套文档**不是**一份固定清单——它是一个很小的**核心**，加上仅在实际存在对应能力时才添加的**条件性**文档。

- **核心文档**——每个可评审的应用都有这些表面，所以始终要产出。
- **条件性文档**——只在应用确实具备该能力时才纳入。如果没有，就在 `architecture.md` 里写一行（「无定时任务——不设 `cron.md`。」），而不是编造一份空文档。可评审性来自一张诚实的图，而「我们不做 X」是这张图的一部分。
- 大多数文档是由 `/document-app` 从代码反向工程出来的。唯一的例外是 `tests.md`，它由 `/derive-tests` *从其他文档推导*而来——它是验证映射，而不是对某个子系统的描述。

对当前状态要极其诚实，但不要多疑。工作目标是准确的地图，而不是一张干净的健康证明。每份文档都很短、以表格和要点为主、跳过通用理论。

## 核心文档

每条都列出：默认文件名 · 一句话目的 · 必须记录什么 · 评审者如何使用。

1. **`architecture.md`**——系统是什么、各部分如何拼在一起。
   - 必须记录：产品概览 + 关键假设；技术栈；身份认证/会话/claim 端到端如何流动；信任边界（例如 service-role 与客户端之间）；一份简短的**已知风险 / 假设**清单（每条都要用它在代码中出现的位置作支撑，而不是泛泛的检查清单）；一份「相关文档」索引，列出产出的所有其他文档。
   - 评审者用法：根文档——其他一切都在这里被交叉引用。

2. **`flows.md`**——权限与副作用真正被执行的用户旅程。
   - 必须记录：每条承重流程，写成 行为人 + 前置条件 + 成功结果；跨 UI → 服务端 → 数据 → 任务 → 提供方 → 智能体的分步序列；**每个受保护步骤处的授权检查**（哪个 claim/角色/scope、作用在哪个资源上，以及预期的*拒绝*情形）；**信任边界穿越**（浏览器→服务端、服务端→提供方、任务→应用、智能体→工具、webhook→应用）；每一步引起的状态变化和副作用（写入、排入队列的邮件、触发的任务、出站调用）。
   - 评审者用法：静态的 `permissions.md` 矩阵无法呈现的运行时视图——授权在*哪里*、*以什么顺序*被强制执行，又在哪里可以被跳过。
   - **反 PRD 规则：** 一条不涉及权限、数据完整性、外部副作用、金钱、隐私或运维安全的流程不该放在这里。这是安全/运维地图，不是功能规格说明。

3. **`permissions.md`**——谁被允许做什么。
   - 必须记录：角色/claim；scope 在哪里派生（token 还是数据库）；一张 资源 × 操作 × 角色 矩阵；哪些表有行级安全、哪些依赖代码强制的检查。
   - 评审者用法：访问控制审计用来与代码作比较的基线。`flows.md` 展示它运动中的样子；这里是静态参照。

4. **`variables.md`**——配置与密钥，映射到风险。
   - 必须记录：一张 名称 · 使用方 · 范围（服务端/客户端）· 来源 · 轮换 · 风险 的表；明确确认没有任何密钥被打进客户端；一份上线前检查清单。
   - 评审者用法：密钥/PII 泄漏面，以及事件响应期间的轮换计划。

5. **`tests.md`**——验证映射：哪些有文档的规则真的被检查、哪些只是提议、哪些完全无人检查。
   - 必须记录，分三个清晰分开的区段，使这张图不会读起来假绿：
     - **现有覆盖**——*今天*就在仓库里的测试，每条都绑定到它所钉住的规则（这样这张图反映的是现实，而不是愿望清单）。
     - **提议的测试**——尚未编写但建议的用例，按**测试类型**标注（自动化单元/集成 · 受保护的实机运行 · 人工评审）。
     - **缺口**——完全没有任何验证的有文档规则，按跨越它们所暴露的东西排序。
   - 每一行都要带上：用例 → 规则 → 预期行为（包括拒绝/否定情形）→ 证据来源（文档 + 代码）→ 状态（已有 / 提议 / 无）。它还要说明仓库的门禁要求哪些检查：按仓库声明的门禁策略（例如一条本地命令加一次人工放行），或者，在仓库没有声明时，说明限制合并到 `main` 的 CI 检查。
   - 评审者用法：「有文档 == 已实现」的可操作形态——它显示其他文档声称的每条规则，今天是真被一条测试钉住了、只是被提议，还是未经验证。
   - 由 `/derive-tests` 产出（不是 `/document-app`），因为它是从其他文档和现有测试套件推导出来的，而不是从某个子系统读出来的。

## 条件性文档（仅在具备对应能力时纳入）

6. **`emails.md`**——系统发送的每一类通知。*仅在应用发送事务性邮件或自动邮件时纳入。*
   - 必须记录：队列 → 处理器 → 提供方 的路径；模板及其接受的变量；重试/退避行为；发送失败时到哪里查看。
   - 评审者用法：发现未校验的模板输入和 PII 暴露边界。

7. **`cron.md`**——所有定时工作，以及如何安全地操作它。*仅在存在定时任务或后台任务时纳入。*
   - 必须记录：一张清单表（任务 → 调度 → 函数 → 密钥 → 限额 → 重试）；每个任务如何保持幂等；内部调用如何做身份认证；到哪里查看最近运行情况。
   - 评审者用法：找出可伪造的触发器和无界的后台任务。

8. **`seo.md`**——单页应用如何处理 SEO 与社交预览。*仅在存在公开/可索引或面向机器人的路由时纳入。*
   - 必须记录：预览方案（静态 meta / 预渲染 / 边缘 HTML）；一张 路由 → 是否需要 SEO → 是否仅公开数据 的表；动态元数据如何被净化；机器人路由与人类路由的区分。
   - 评审者用法：抓住「仅公开数据」的违规和机器人路由上的元数据注入。

9. **`automation.md`**——内嵌的智能体与其他自动化路径。*仅在应用内嵌 AI 智能体、LLM 工作流、工具调用、webhook 或外部自动化时纳入。*
   - 必须记录，按每个自动化/智能体：触发方式 + 所有者 + 是自动运行还是仅在批准后运行；它可以读取的输入；以及**它实际可以调用的工具/API**（工具面本身就是一道硬护栏）；**引导**（提示词）放在哪里，与**提示词之外的硬护栏**放在哪里；回到应用的**输出契约**（schema、校验、失败处理）；**应用拥有的副作用与智能体拥有的建议**；以及各项控制——审批门、审计/时间线日志、速率限制、重试、终止开关。
   - 评审者用法：让隐藏的自动化路径变得可见，并划清智能体*提议*什么与应用*强制执行*什么之间的界线——这是现代 AI 编写的应用里风险最高的表面。

## 备注

- 每份产出的文档都要在 `architecture.md` 的「相关文档」一节（或仓库已经为它的文档维护的索引里）加上指向自己的引用，这样整套文档始终可被发现。
- 跳过任何不适用的条件性文档，并用一行说明，而不是编造内容。
- 不要把示例和成品模板放进这些文档——它们描述的是*这个*系统，不是通用方法。
- 智能体操作上下文文件（`AGENTS.md` 或 `CLAUDE.md`，取仓库结构中被视为标准的那一个）是一份*不同的*产物——它是从这些文档派生出的指令，而不是系统文档。它由 `/ship-check` 在交接步骤产出，而 `/ship-check` 遵循那种结构，不是在这里。
- `tests.md` 由 `/derive-tests` 产出；其余由 `/document-app` 产出。
- 沿用仓库的日期约定。如果仓库没有约定，就不要写「更新日期」行；文件历史才是权威来源。
