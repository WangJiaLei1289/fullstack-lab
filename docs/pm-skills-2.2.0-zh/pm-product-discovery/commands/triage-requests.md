# /triage-requests —— 功能需求分级处理

把一大堆积压的功能需求——来自客服工单、销售电话、问卷或 Slack——变成一份排好优先级、可直接执行的待办列表。

## 调用方式

```
/triage-requests                           # 索取输入
/triage-requests [粘贴一列需求]
/triage-requests [上传 CSV/表格]
```

## 工作流程

### 第 1 步：接收功能需求

任何格式的需求都可以：
- **粘贴文本**：一列需求，每行或每段一条
- **上传文件**：CSV、Excel 或含需求数据的文本文件
- **结构化数据**：如果输入带字段（提出人、需求、日期等），保留这些字段

如果没有提供输入，请用户粘贴或上传功能需求。

解析每条需求，提取：
- 核心诉求（用户想要什么）
- 背景（谁提的、什么时候、为什么——如有）
- 频次信号（有多少人提了类似的需求）

### 第 2 步：收集排优先级的背景信息

以对话方式询问用户（不要一次问完）：
- 产品是什么？处于什么阶段？
- 当前的战略目标或 OKR 是什么？（便于评估契合度）
- 有哪些约束需要考虑？（团队规模、技术债、临近的截止日期）
- 有没有哪些用户细分群体的需求应当加权？（企业客户、流失中的用户、重度用户）

### 第 3 步：归类与分析

应用 **analyze-feature-requests** 技能：

- **主题聚类**：把相似需求归入同一主题（例如「报表与分析」「协作」「移动端体验」）
- **每个主题的需求数量**：每个主题对应多少条独立需求
- **战略契合度**：对照既定目标给每个主题打分（高/中/低/无）
- **细分群体分析**：哪些用户细分在推动哪些主题
- **情绪信号**：这些需求背后是否伴随挫败感、流失威胁或惊喜

### 第 4 步：排优先级

应用 **prioritize-features** 技能：

对每个主题（以及每个主题内排名靠前的单条需求）：

| 因素 | 评估 |
|--------|-----------|
| **影响** | 影响多少用户？有多严重？ |
| **战略契合度** | 是否服务于当前目标？ |
| **工作量估算** | T 恤尺码（S/M/L/XL） |
| **风险** | 如果不做会怎样？ |
| **营收信号** | 是否与成单、留存或增购相关？ |

给主题排序，产出优先级清单。

### 第 5 步：生成分级处理报告

```
## 功能需求分级处理报告

**日期**：[今天]
**分析的需求数**：[数量]
**识别出的主题数**：[数量]

### 主题汇总
| # | 主题 | 需求数 | 核心诉求 | 契合度 | 影响 | 投入 | 优先级 |
|---|-------|----------|---------|-----------|--------|--------|----------|

### 优先级 1：立即行动
[应纳入近期规划的主题/需求]
- **[主题]**：[X] 条需求 —— [为什么紧急]
  - 需求 top 列表：[清单]
  - 建议动作：[开发 / 做原型 / 调研]

### 优先级 2：下一轮规划
[值得规划但不紧急的主题]

### 优先级 3：继续收集信号
[有潜力但证据不足的主题]

### 优先级 4：拒绝或延后
[不符合战略的需求——附理由]

### 值得单独提的需求
[价值高但未能聚类成主题的一次性需求]

### 模式与洞察
- [关于用户在告诉你什么的关键洞察]
- [按用户细分的模式]
- [用户诉求与底层需求之间的差距]
```

把报告保存为用户工作目录下的 markdown 文件。

### 第 6 步：给出后续建议

- 「需要我为优先级最高的事项**写用户故事**吗？」
- 「需要我针对其中某些主题**头脑风暴解决方案**吗？」
- 「需要我先**设计实验**验证需求，再动手开发吗？」
- 「需要我**起草一份利益相关方更新**，汇总这次分析吗？」

## 注意事项

- 如果用户提供的 CSV 带列，保留数据结构并在此基础上补充信息
- 找需求背后的真实需要——「加暗色模式」可能真正想说的是「长时间使用别那么伤眼」
- 标出彼此冲突的需求（例如「简化界面」与「增加更多配置项」）
- 如果需求量很大（50 条以上），先汇总主题，再按需深入某个主题
- 如果输入是结构化数据，把补充信息后的数据导出为可下载的 CSV
