# /setup-metrics —— 产品指标看板设计

为你的产品或功能设计一套完整的指标体系——从选定合适的北极星指标，到定义能及早发现问题的告警阈值。

## 调用方式

```
/setup-metrics SaaS 项目管理工具
/setup-metrics 我们刚上线的新结账流程
/setup-metrics             # 询问你要度量什么
```

## 工作流程

### 第 1 步：明确要度量什么

询问用户：
- 你要为哪个产品或功能领域搭建指标？
- 它处于什么阶段？（未上线、刚上线、成熟）
- 当前的业务目标或 OKR 是什么？
- 已有指标吗？缺什么、哪里坏了？
- 你在用什么分析工具？（便于给出贴合实际的落地建议）

### 第 2 步：定义指标体系

应用 **metrics-dashboard** 技能：

**北极星指标：**
- 找出最能代表「产品为用户交付价值」的那一个指标
- 用以下标准校验：能衡量价值交付、是先行指标、可行动
- 精确定义该指标（公式、数据来源、统计时间窗口）

**输入指标（3-5 个）：**
- 找出驱动北极星指标的杠杆
- 每个输入指标都应能被某个团队直接推动
- 画出因果链：输入 → 北极星指标 → 业务结果

**健康指标（3-5 个）：**
- 这些指标应当保持稳定——一旦恶化，说明出了问题
- 例如：错误率、延迟、客服工单量、NPS、流失率
- 定义「健康」区间和恶化阈值

**反向指标（1-2 个）：**
- 用来提示你可能在朝错误方向优化的指标
- 例如：若北极星指标是「日活用户」，反向指标就选「会话质量」，以防刷出无意义的活跃

### 第 3 步：设计告警阈值

为每个指标设定：

| 指标 | 绿色 | 黄色 | 红色 | 检查频率 |
|--------|-------|--------|-----|----------------|
| [指标] | [健康区间] | [警告] | [严重] | [每天/每周] |

- **黄色**：介入排查——可能出了问题
- **红色**：立即行动——通知值班人或上报

### 第 4 步：产出看板规格

```
## 指标看板：[产品/功能]

**北极星指标**：[指标名称]
**定义**：[精确公式]
**当前值**：[如已知]
**目标**：[目标值]

### 输入指标
| 指标 | 定义 | 负责人 | 目标 | 当前 |
|--------|-----------|-------|--------|---------|

### 健康指标
| 指标 | 健康区间 | 黄色阈值 | 红色阈值 |
|--------|-------------|-----------------|---------------|

### 反向指标
| 指标 | 为什么重要 | 需要关注什么 |
|--------|---------------|-----------|

### 指标树
北极星指标：[指标]
├── 输入：[指标 1] → 由 [团队/动作] 驱动
├── 输入：[指标 2] → 由 [团队/动作] 驱动
├── 输入：[指标 3] → 由 [团队/动作] 驱动
└── 反向：[指标] → 关注 [恶化信号]

### 落地说明
- 数据来源：[每个指标的数据出处]
- 刷新频率：[实时 / 每小时 / 每天]
- 工具建议：[基于用户现有的技术栈]

### 复盘节奏
- **每天**：扫一眼北极星指标和健康指标
- **每周**：看输入指标趋势，在团队站会上讨论
- **每月**：深入分析——输入指标是否如预期驱动了北极星指标？
- **每季度**：重新评估指标体系本身
```

保存为用户工作目录下的 markdown 文件。

### 第 5 步：给出后续建议

- 「需要我**写 SQL 查询**来计算这些指标吗？」
- 「需要我基于这套指标体系**制定 OKR** 吗？」
- 「需要我做一份**同期群分析**来设定合理的基线吗？」
- 「需要我**搭一个每周指标复盘模板**吗？」

## 注意事项

- 好的北极星指标很少见——多数团队选的是虚荣指标。要力争一个能体现*为用户交付的价值*的指标，而不只是参与度
- 输入指标在解释北极星指标时应当满足 MECE（相互独立、完全穷尽）
- 如果产品尚未上线，先把指标定义出来，但要说明基线需要在上线后校准
- 反向指标可以防止古德哈特定律——指标一旦成为目标，就不再是好指标
- 建议少而精：先把少量指标埋点做扎实，好过铺一片没人看的看板
