# 编写技能

## 概述

**写技能就是测试驱动开发应用在流程文档上。**

**个人技能放在你的运行时的技能目录里**（Claude Code 上是 `~/.claude/skills/`）——其他运行时上的路径见 [codex-tools.md](../using-superpowers/references/codex-tools.md) 或 [gemini-tools.md](../using-superpowers/references/gemini-tools.md)。Codex、Copilot CLI 和 Gemini CLI 也都认得 `~/.agents/skills/`，它是跨运行时的别名。

你先写测试用例（带子代理的压力场景），看着它们失败（基线行为），再写技能（文档），看着测试通过（代理服从），最后重构（堵住漏洞）。

**核心原则：**如果你没有亲眼看着代理在没有技能时失败，你就不知道这个技能教的是不是正确的东西。

**所需背景：**使用本技能之前，你必须先理解 superpowers:test-driven-development。那个技能定义了根本的 RED-GREEN-REFACTOR 循环。本技能把 TDD 适配到文档上。

**官方指南：**Anthropic 官方的技能编写最佳实践见 references/anthropic-best-practices.md。那份文档提供了额外的模式与指南，与本技能以 TDD 为核心的做法互补。

## 什么是技能？

**技能**是一份参考指南，介绍经过验证的技术、模式或工具。技能帮助未来的代理找到并应用有效的做法。

**技能是：**可复用的技术、模式、工具、参考指南

**技能不是：**关于你某次如何解决某个问题的叙事

## 技能的 TDD 对照

| TDD 概念 | 技能创建 |
|-------------|----------------|
| **测试用例** | 带子代理的压力场景 |
| **生产代码** | 技能文档（SKILL.md） |
| **测试失败（RED）** | 没有技能时代理违规（基线） |
| **测试通过（GREEN）** | 有技能时代理服从 |
| **重构** | 在保持服从的前提下堵住漏洞 |
| **先写测试** | 在写技能之前先跑基线场景 |
| **看着它失败** | 记录代理使用的确切自我合理化说辞 |
| **最小代码** | 写出针对这些具体违规的技能 |
| **看着它通过** | 验证代理现在服从 |
| **重构循环** | 发现新的自我合理化 → 堵上 → 重新验证 |

整个技能创建过程都遵循 RED-GREEN-REFACTOR。

## 何时创建技能

**在以下情况创建：**
- 这项技术对你来说并不是直觉上显然的
- 你会跨项目反复参考它
- 这个模式适用范围广（不是项目专用的）
- 其他人也能从中受益

**不要为以下情况创建：**
- 一次性的解决方案
- 别处已有充分文档的标准实践
- 项目专用的约定（写进你的指令文件）
- 机械性约束（如果可以用正则/校验强制执行，就自动化它——把文档留给需要判断的地方）

## 技能类型

### 技术（Technique）
有步骤可循的具体方法（condition-based-waiting、root-cause-tracing）

### 模式（Pattern）
思考问题的方式（flatten-with-flags、test-invariants）

### 参考（Reference）
API 文档、语法指南、工具文档（office docs）

## 目录结构


```
skills/
  skill-name/
    SKILL.md              # Main reference (required)
    supporting-file.*     # Only if needed
```

**扁平命名空间**——所有技能都在同一个可搜索的命名空间里

**需要拆成单独文件的：**
1. **重型参考**（100 行以上）——API 文档、完整的语法说明
2. **可复用的工具**——脚本、实用程序、模板

**保持内联：**
- 原则与概念
- 代码模式（少于 50 行）
- 其他一切

## 编写 SKILL.md

技能的 `description` 只说明何时使用它：触发条件和症状，以「Use when...」开头。它绝不概括技能的工作流程，因为读了工作流摘要的代理会照着摘要去做，而不去读技能本身。

当你编写或修改技能的 frontmatter、名称或 description，或者需要压缩它的篇幅时，先读 [references/discovery.md](references/discovery.md)：里面有 SKILL.md 模板、description 与关键词指南、命名、token 预算，以及如何交叉引用其他技能。

## 流程图

当你在技能里新增或修改流程图时，先读 [references/flowcharts.md](references/flowcharts.md)：流程图什么时候才值得存在、graphviz 的约定，以及如何渲染。

## 代码示例

**一个出色的示例胜过许多平庸的示例**

选择最相关的语言：
- 测试技术 → TypeScript/JavaScript
- 系统调试 → Shell/Python
- 数据处理 → Python

**好示例：**
- 完整且可运行
- 注释充分，解释「为什么」
- 来自真实场景
- 清楚地展示模式
- 拿来就能改（不是通用模板）

**不要：**
- 用 5 种以上语言各实现一遍
- 造填空式模板
- 写刻意拼凑的示例

你很擅长移植——一个出色的示例就够了。

## 文件组织

### 自包含技能
```
defense-in-depth/
  SKILL.md    # Everything inline
```
适用：所有内容都放得下，不需要重型参考

### 带可复用工具的技能
```
condition-based-waiting/
  SKILL.md    # Overview + patterns
  example.ts  # Working helpers to adapt
```
适用：工具是可复用的代码，而不只是叙述

### 带重型参考的技能
```
pptx/
  SKILL.md       # Overview + workflows
  pptxgenjs.md   # 600 lines API reference
  ooxml.md       # 500 lines XML structure
  scripts/       # Executable tools
```
适用：参考资料太大，不适合内联

通过解释器在正文里调用随包脚本（`bash scripts/tool.sh`、`node scripts/tool.js`），绝不要用裸路径：有些宿主环境的插件打包器会剥掉可执行位，裸写 `scripts/tool.sh` 在那里会报 `Permission denied`。

## 铁律（和 TDD 一样）

```
NO SKILL WITHOUT A FAILING TEST FIRST
```

这既适用于新技能，也适用于对现有技能的修改。

先写技能再测试？删掉。重新开始。
改技能却不测试？同样的违规。

**没有例外：**
- 不因为「只是简单加一点」
- 不因为「只是加一节」
- 不因为「更新文档」
- 不要把没测过的改动留着当「参考」
- 不要在跑测试的同时「顺手调整」
- 删掉就是删掉

**所需背景：**superpowers:test-driven-development 技能解释了为什么这很重要。同样的原则也适用于文档。

## 测试所有类型的技能

不同技能类型需要不同的测试方法：

### 强制纪律的技能（规则/要求）

**示例：**TDD、verification-before-completion、designing-before-coding

**测试方式：**
- 学术性问题：他们理解规则吗？
- 压力场景：他们在压力下仍然服从吗？
- 多重压力叠加：时间 + 沉没成本 + 疲惫
- 找出自我合理化说辞，并加上明确的针对性反制

**成功标准：**代理在最大压力下仍然遵守规则

### 技术类技能（操作指南）

**示例：**condition-based-waiting、root-cause-tracing、defensive-programming

**测试方式：**
- 应用场景：他们能正确应用这项技术吗？
- 变体场景：他们能处理边界情况吗？
- 信息缺失测试：指令里有没有缺口？

**成功标准：**代理能把这项技术成功应用到一个新场景

### 模式类技能（心智模型）

**示例：**reducing-complexity、information-hiding concepts

**测试方式：**
- 识别场景：他们能识别出模式何时适用吗？
- 应用场景：他们会用这个心智模型吗？
- 反例：他们知道什么时候**不该**用吗？

**成功标准：**代理能正确判断何时、如何应用这个模式

### 参考类技能（文档/API）

**示例：**API 文档、命令参考、库指南

**测试方式：**
- 检索场景：他们能找到正确的信息吗？
- 应用场景：他们能正确使用找到的信息吗？
- 缺口测试：常见用例都覆盖了吗？

**成功标准：**代理能找到并正确应用参考信息

## 跳过测试时的常见自我合理化

| 借口 | 现实 |
|--------|---------|
| 「技能明显很清楚」 | 对你清楚 ≠ 对其他代理清楚。去测。 |
| 「它只是个参考」 | 参考也可能有缺口、有含糊的章节。测检索。 |
| 「测试是过度了」 | 没测过的技能一定有问题。永远如此。15 分钟测试省下的是几小时。 |
| 「出问题了我再测」 | 出问题 = 代理用不了这个技能。要在**部署前**测。 |
| 「测起来太繁琐」 | 测试比在生产里调试烂技能要不繁琐得多。 |
| 「我确信它没问题」 | 过度自信必然带来问题。照样去测。 |
| 「学术性评审就够了」 | 读 ≠ 用。要测应用场景。 |
| 「没时间测」 | 部署没测过的技能，之后修它要浪费更多时间。 |

**这些都意味着：部署前先测试。没有例外。**

## 让表达形式匹配失败类型

在写指导之前，先给基线失败分类。对一种失败类型能起到防弹效果的形式，换到另一种失败上却会实测出明显的反噬。

| 基线失败 | 正确的形式 | 错误的形式 |
|---|---|---|
| 在压力下跳过/违反规则（明明知道更好，还是这么做） | 禁止 + 自我合理化表 + 危险信号（见 references/bulletproofing.md） | 软性指导（「优先……」「可以考虑……」） |
| 服从了，但输出的形状不对（提示词臃肿、结论被埋没、重述规格） | 正向配方或契约：说明输出**是**什么——包含哪些部分、以什么顺序 | 禁止清单（「不要重述」「绝不叙述」） |
| 在他本来就会产出的东西里漏掉一个必需元素 | 结构性：在他要填的模板里设 REQUIRED 字段或槽位 | 在模板附近写散文式提醒 |
| 行为应当取决于某个条件 | 以可观察谓词为键的条件式（「如果简报存在，就引用它」） | 无条件规则 + 豁免条款 |

**为什么禁止式在「塑形」问题上会反噬：**面对相互竞争的激励（「让提示词自成一体」），代理会和「不要 X」讨价还价。在针对分派提示词指导的正面对比措辞测试中，禁止式那一组的产出明显比配方式那一组包含更多不想要的内容（分布完全分开），甚至比无指导的对照组趋势更差——所以要对你的具体场景做微测试，而不是想当然，但也绝不要默认伸手去用禁止式。配方式没有留下任何可谈判的空间：输出要么符合声明的形状，要么不符合。

**无论选哪种形式，规则如下：**
- **不要写细微差别条款。**「除非确实重要，否则不要做 X」这样的条款等于重新打开谈判——在同批措辞测试里，给一个胜出的配方追加一条细微差别条款，就把它从稳定退化成了噪声。真正的例外要写成以可观察谓词为键的独立条件式。
- **豁免条款并不限定范围。**「这个限制不适用于代码块」仍然会压制代码块。如果输出的一部分必须豁免，就重构结构，让规则够不到它。

## 抵御自我合理化

当基线失败属于纪律型失败时，先读 [references/bulletproofing.md](references/bulletproofing.md)，再写指导：包括堵漏洞、精神与字面之分的界限、自我合理化表，以及危险信号清单。

## 技能的 RED-GREEN-REFACTOR

遵循 TDD 循环：

### RED：写会失败的测试（基线）

在没有技能的情况下，用子代理跑压力场景。记录确切的行为：
- 它做了哪些选择？
- 它用了哪些自我合理化说辞（逐字）？
- 哪些压力触发了违规？

这就是「看着测试失败」——你必须在写技能之前，看到代理自然会怎么做。

### GREEN：写出最小技能

写出针对这些具体自我合理化说辞的技能。不要为假设中的情况添加额外内容。

带着技能跑同样的场景。代理现在应该服从。

### REFACTOR：堵住漏洞

代理找到了新的自我合理化？加上明确的反制。重测，直到防弹。

### 在完整场景之前先微测措辞

完整的压力场景跑法是最后的门禁，但每次迭代都又慢又贵。先用微测试验证措辞本身：

1. **每次调用用一个全新上下文的样本**——直接发一次原始 API 调用，如果没有 API 访问权限，就用单次子代理。系统提示词 = 这段指导将要栖身的真实上下文（完整的技能或提示词模板，而不是孤立的指导）；用户消息 = 一个会诱发该失败的任务。
2. **永远带上无指导对照组。**如果对照组没有表现出该失败，那就没有需要修的东西——停下，不要写这段指导。
3. **每个变体 5 次以上重复。**单次样本会骗人。
4. **人工读遍每一个被标记的命中。**你可以用程序打分，但模板回显和被引用的反例会伪装成命中；只靠自动计数会同时高估失败和成功。
5. **方差本身就是一个指标。**指导生效时，重复样本会收敛到同一种形状。五次重复给出五种不同解读，说明措辞没有约束力——先收紧形式，再增加字数。

微测试验证的是措辞；它们不能替代针对纪律型技能的压力场景。

**测试方法论：**完整的测试方法论见 [references/testing-skills-with-subagents.md](references/testing-skills-with-subagents.md)：
- 如何编写压力场景
- 压力类型（时间、沉没成本、权威、疲惫）
- 系统性地堵洞
- 元测试技巧

## 反模式

### ❌ 叙事型示例
「在 2025-10-03 那次会话里，我们发现空 projectDir 导致……」
**为什么不好：**太具体，无法复用

### ❌ 多语言稀释
example-js.js、example-py.py、example-go.go
**为什么不好：**质量平庸，维护负担重

### ❌ 流程图里写代码
```dot
step1 [label="import fs"];
step2 [label="read file"];
```
**为什么不好：**无法复制粘贴，难读

### ❌ 通用标签
helper1、helper2、step3、pattern4
**为什么不好：**标签应当有语义

## 停：在进入下一个技能之前

**写完任何技能之后，你必须停下来，走完部署流程。**

**不要：**
- 不逐个测试就批量创建多个技能
- 当前这个还没验证就进入下一个
- 因为「批量更高效」就跳过测试

**下面这份部署检查清单对每一个技能都是强制性的。**

部署没测过的技能 = 部署没测过的代码。这是违反质量标准的行为。

## 技能创建检查清单（TDD 改编版）

**重要：为下面清单里的每一项创建一个 todo。**

**RED 阶段——写会失败的测试：**
- [ ] 创建压力场景（纪律型技能需 3 个以上叠加的压力）
- [ ] 在没有技能的情况下跑场景——逐字记录基线行为
- [ ] 找出自我合理化/失败中的模式

**GREEN 阶段——写出最小技能：**
- [ ] 名称只用字母、数字、连字符（不要括号/特殊字符）
- [ ] 带必需的 `name` 和 `description` 字段的 YAML frontmatter（最多 1024 个字符；见 [spec](https://agentskills.io/specification)）
- [ ] description 以「Use when...」开头，并包含具体的触发条件/症状
- [ ] description 用第三人称写
- [ ] 通篇埋入关键词以便搜索（错误、症状、工具）
- [ ] 有清晰的概述和核心原则
- [ ] 针对 RED 阶段找出的具体基线失败
- [ ] 指导形式与失败类型匹配（见「让表达形式匹配失败类型」）
- [ ] 对塑造行为的指导：措辞已对照无指导对照组做过微测（5 次以上重复，每个被标记的命中都人工读过）——纯参考型技能不适用
- [ ] 代码内联，或者链接到单独文件
- [ ] 一个出色的示例（不是多语言版）
- [ ] 带着技能跑场景——验证代理现在服从

**REFACTOR 阶段——堵住漏洞：**
- [ ] 从测试中找出**新的**自我合理化说辞
- [ ] 加上明确的反制（如果是纪律型技能）
- [ ] 用所有测试迭代构建自我合理化表
- [ ] 创建危险信号清单
- [ ] 重测，直到防弹

**质量检查：**
- [ ] 只有在决策不明显时才配一张小流程图
- [ ] 快速参考表
- [ ] 常见错误一节
- [ ] 没有叙事式讲故事
- [ ] 支持性文件只用于工具或重型参考

**部署：**
- [ ] 把技能提交到 git 并推送到你的 fork（如果已配置）
- [ ] 考虑通过 PR 回馈上游（如果广泛有用）

## 发现流程

未来的代理如何找到你的技能：

1. **遇到问题**（「测试很不稳定」）
2. **搜索技能**（grep 描述、浏览分类）
3. **找到 SKILL**（description 匹配）
4. **扫一眼概述**（这相关吗？）
5. **读模式**（快速参考表）
6. **加载示例**（只在实现时）

**针对这个流程做优化**——把可搜索的词放在前面、反复出现。
