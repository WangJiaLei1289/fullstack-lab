# 诊断 superpowers

## 概览

与你的搭档一起确定会话中到底哪里出了问题，读取磁盘上的对话记录，并带着证据报告发生了什么。你负责报告；你不负责诊断 superpowers。由分诊交付包或 issue 的人决定 superpowers 是否要改。

**核心原则：** 每条发现都要引用 `path:line`。没有引用，就没有发现。每个数字都来自对话记录，或来自你实际运行过的命令，绝不凭记忆。

## 工作流程

每个步骤都建一条待办。第 5–7 步只在其声明的条件满足时才执行。

1. **问题收集。** 一次只问一个问题，直到你能写出一段陈述：指明是哪个（些）会话、已知的轮次范围、你的搭档原本期待什么、实际发生了什么，以及对方关心的那个可观测量（实际耗时、token、重复动作，或某一个具体动作）。「耗时太久」是抱怨，不是问题陈述。记下目标是否是给 superpowers 提 bug 报告。
2. **定位。** 使用 `references/session-discovery.md` 把每个会话解析为经过核实的文件系统绝对路径。通过引用第一个提示词和时间戳来确认过往会话，并列出每个被排除的候选及原因，或者写「无」。枚举子代理的对话记录。创建 `~/.superpowers/diagnosing-superpowers/<session-id>/`，把路径告诉你的搭档，并在其中填写 `templates/case.md`，遵循它关于环境与技能观测的来源规则。
3. **分诊。** 你自己先读问题报告附近的区域。然后并行分派每个维度一个分析师子代理，每个都拿到案例文件路径、`prompts/analyst-common.md`，以及 `prompts/` 下的一个维度文件：`skill-timeline.md`、`plan-adherence.md`、`repeated-work.md`、`stumbles.md`、`quality-evidence.md`、`request-conflicts.md`、`cost-and-time.md`。对话记录很长时，按轮次范围切分维度。丢弃任何没有 `path:line` 的返回发现。
4. **报告。** 按顺序填写 `templates/report.md` 的每一节，写入工作区，展示出来，并给出路径。核对所引用的内容究竟能证明什么，并保留支撑性案例；符号链接别名不是冗余副本。
5. **GitHub issue** —— 当报告第 7 节指出可能或很可能时，或你的搭档要求时。按 `references/github-issues.md` 搜索开启中和已关闭的 issue 来寻找对应症状。展示匹配项，并建议把报告补充到最接近的那个。如果没有匹配，填写 `templates/issue.md`，写入工作区，展示确切文本，并且只有在获得批准后才创建 issue。`gh` 无法附加文件；如果已有交付包，把它的路径给你的搭档，让对方在浏览器中附加。
6. **导出** —— 只有你的搭档要求交付包时才做；绝不在未被要求时自行构建。如果问题收集阶段的目标就是 bug 报告，只说一次「可按需提供已清洗的交付包」，然后等待。询问脱敏级别，并说明每一级包含什么：skeleton（不含工具结果正文）、evidence（只含被引用事件的正文）、full。按 `templates/bundle-README.md` 构建交付包，分派 `prompts/scrub.md`，再分派 `prompts/scrub-audit.md`，两者反复执行，直到审计返回 CLEAN。先完成交付包模板中的证据核对与对账，再展示最终的 scrub 日志、文件清单，以及隐私与证据层面的结果。只有在获得批准后才归档（`zip -r` 或 `tar -czf`）。给出归档路径时，要说明它包含什么，指向 scrub 日志查看替换内容，并说明清洗可能漏掉东西：对方必须在分享前逐一检查每个文件。
7. **相似会话** —— 在被要求时。把已确认的发现转成一个特征签名，按修改时间和大小列出候选，找到标记行号，对每个候选并行分派 `prompts/similar-session.md`，并追加到报告第 9 节。

## 快速参考

七个分析师总是全部运行。这张表说明在第 3 步中你自己该先读哪个区域，以及在结论中该先报哪些发现。

| 抱怨 | 先读什么，先报什么 |
|---|---|
| 「耗时太久」 | cost-and-time、stumbles |
| 「它为什么做这些多余的工作？」 | repeated-work、plan-adherence |
| 「为什么这么贵？」 | cost-and-time |
| 「它到底在搞什么？」（仍在运行） | skill-timeline；在覆盖范围里注明仍在进行 |
| 「它无视了计划」 | plan-adherence，先看 compaction 记录行 |
| 「技能 X 从未触发」 | skill-timeline |

## 硬性规则

- **上下文安全。** 一行对话记录可能有一兆字节。每次处理每个会话文件时，都遵循 `references/context-safety.md`。
- **只读。** 绝不修改、移动或删除会话文件。
- **给子代理的必须是确切路径。** 子代理的「当前会话」是它自己的会话。传绝对路径和 id。
- **只认人类提示词。** 钩子输出、系统提醒和工具结果都不是你搭档说的话。在子代理的对话记录里，「user」指的是父代理。
- **不做 superpowers 诊断。** 报告第 7 节只陈述是否相关，然后就停。绝不说某个技能有缺陷，也不提出改动建议。搭档催着要修复也不能豁免这一条；指向 issue 步骤，并说明交付包可按需提供。也不要给搭档建议。
- **批准门禁。** 在你的搭档看过 scrub 日志和文件清单之前，不得归档。在对方批准确切文本之前，不得创建 issue 或评论；也不得使用占位摘要。
- **先收集再分析。** 在搭档回答之前，第 2–7 步的任何动作都不能开始。如果对方不在，就把问题写下来，然后停下。你替对方重构出来的陈述不是回答。一个已经限定范围的请求 —— 某个具体事件、现在正在运行什么，或要跑哪项分析 —— 本身就是问题陈述：先回答它，再提问。针对整个会话的「为什么」是抱怨。

## 危险信号

| 想法 | 现实 |
|---------|---------|
| 「问题很明显，跳过问题收集」 | 问题陈述决定一切范围。去问。 |
| 「对方不在，那我替对方重构陈述」 | 你无法重构对方想要什么。把问题写下来，停下。 |
| 「我现在把所有东西都扫一遍，最后再问」 | 没有范围的扫描会把对方的预算花在错误的问题上。先问。 |
| 「对方要 bug 报告，所以我现在就打包」 | 交付包是对方会话数据的打包。只有对方要求时才构建。 |
| 「只是小范围定向修改，不需要重构」 | 无论多小，这都不是你能定的。报告证据；由分诊者决定。 |
| 「每个 token 的价格是众所周知的」 | 你没有从对话记录中算出来的数字就是编造的。引用或删掉。 |
