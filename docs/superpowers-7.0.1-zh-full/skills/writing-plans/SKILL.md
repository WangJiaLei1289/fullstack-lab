# 撰写计划

## 概览

为一个没看过这个代码库、也没看过这份规格的工程师写实现计划。假定：只要知道确切的接口和确切的测试，他们就能用项目的语言写出地道的代码；计划里留待选择的地方，他们都会做出合理的决定。他们不可能知道的是你做的决定：哪些文件、哪些名称与签名、规格里的哪些取值、哪些测试能证明每个任务。把这些写下来。把整份计划拆成一口大小的任务交给他们。DRY。YAGNI。TDD。频繁提交。

**开始时宣告：** "I'm using the writing-plans skill to create the implementation plan."（我正在使用 writing-plans 技能来创建实现计划。）

**上下文：** 如果在隔离的工作树（worktree）中工作，这个工作树应当在执行时通过 `superpowers:using-git-worktrees` 技能创建。

**将计划保存到：** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- （用户对计划存放位置的偏好会覆盖这个默认值）

## 范围检查

如果规格涵盖多个相互独立的子系统，那么在头脑风暴阶段就应该已经把它拆成若干子项目规格。如果没有，建议把它拆成几份独立的计划——每个子系统一份。每份计划都应能独自产出可运行、可测试的软件。

## 文件结构

在定义任务之前，先画出将要创建或修改哪些文件、每个文件负责什么。分解决策就是在这一步定下来的。

- 把单元设计成边界清晰、接口明确。每个文件应只有一项清晰的职责。
- 你对能一次放进上下文的代码推理得最好；文件聚焦时，你的改动也更可靠。优先用更小、更专注的文件，而不是什么都做的大文件。
- 一起变化的文件应该放在一起。按职责拆分，不要按技术分层拆分。
- 在既有代码库中，遵循已有的模式。如果代码库本来就用大文件，不要单方面重构——但如果你正在改的文件已经变得难以驾驭，在计划里安排一次拆分是合理的。

这个结构会反过来指导任务分解。每个任务产生的改动都应是自包含的，单独看也讲得通。

## 任务大小拿捏

一个任务是最小的单位：它自带一个测试周期，并且值得让一位新评审者为它把关。划定任务边界时：把搭建、配置、脚手架和文档步骤并入那个交付物需要它们的任务；只有在评审者可以合理地否掉一个任务、却批准它旁边那个任务的地方，才把任务拆开。每个任务都以一个可独立测试的交付物结束。

## 步骤粒度

**每个步骤是一个动作，有一个可检查的结果：**
- 「写一个会失败的测试」—— 一个步骤
- 「运行它，确认它失败」—— 一个步骤
- 「实现让测试通过的最小代码」—— 一个步骤
- 「运行测试，确认它们通过」—— 一个步骤
- 「提交」—— 一个步骤

## 计划文档头部

**每份计划都必须以这个头部开始：**

```markdown
# [Feature Name] 实施计划

> **面向代理工作者：** REQUIRED SUB-SKILL：使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans，逐个任务地执行这份计划。用复选框（`- [ ]`）语法跟踪进度。

**目标：** [One sentence describing what this builds]

**架构：** [2-3 sentences about approach]

**技术栈：** [Key technologies/libraries]

**规格：** [path to the spec/design doc this plan implements — the plan
论证依据来自规格，所以规格随计划一起走；执行者两边都读]

## 全局约束

[规格中适用于整个项目的要求——版本下限、依赖限制、
命名与文案规则、平台要求——每行一条，具体数值照规格原文
逐字抄录。每个任务的要求都隐含地包含这一节内容，因此
执行时请把这一节当作任务要求的一部分。]

## 审查重点

[规格暗示、但没有任何任务的测试覆盖到的五类输入或失败模式——
也就是最可能让使用这套软件的人吃亏的情况。每行一条，
写明具体的输入或条件，以及一个通情达理的人会期待的行为，
最可能的排在前面。规格是一份愿景文档：它说明软件必须做什么，
而不是说明它会遇到的一切；它对某个输入保持沉默，并不等于
允许那个输入把程序搞坏。在规格就摆在面前的时候，
把这份清单一次性地写在这里。然后针对清单的每一行，
把固定该行为的测试补进拥有那段代码的那个任务里，
并沿用该任务自己的步骤写法。]

---
```

## 任务结构

````markdown
### 任务 N：[Component Name]

**文件：**
- 新建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 消费： [what this task uses from earlier tasks — exact signatures]
- 产出： [what later tasks rely on — exact function names, parameter
  以及返回类型。一个任务的实现者只看得到自己这个任务；
  这一段就是他们了解相邻任务所用名称与类型的方式。]

- [ ] **第 1 步：写一个会失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **第 2 步：运行测试，确认它失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：FAIL，报错为 "function not defined"

- [ ] **第 3 步：在 `exact/path/to/file.py` 中实现 `function(input: InputType) -> ResultType`**

当签名和测试还留有选择余地时，用一句话说明做法
（用哪个库调用、用哪种数据结构）；只有当算法无法由二者确定时，
才写代码块。

- [ ] **第 4 步：运行测试，确认它通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：PASS

- [ ] **第 5 步：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 一个步骤包含什么

一个步骤算完成，是指实现者能从中恰好写出唯一一件合理的事。这就是全部要求：没有歧义，而不是面面俱到。每一类步骤只携带让它没有歧义所必需的东西，不多带：

- **测试步骤：** 测试的名称和它的断言，以代码形式给出，里面带上规格的确切取值。
- **代码步骤：** 确切的签名（名称、参数、返回类型）、它所在的文件，以及规格钉死的具体取值。函数体由实现者写。只有当签名和测试都决定不了某个算法，或者规格固定了某段确切文案时，才给出函数体。
- **验证步骤：** 要运行的命令，以及表示它通过了的输出。
- **对另一个任务的引用：** 那个任务的 Interfaces 区块已经说明该用什么；计划不重复那个任务的代码。

计划是实现者无法独自做出的那组决定。一份比它所描述的代码还长的计划，等于已经把代码写出来了。决定不了任何事的行（「TBD」、「处理边界情况」、「加上适当的校验」、「为上述内容写测试」、某个没有任何任务定义的类型或函数）是另一种失败，而自我检查两种都能抓住。

## 自我检查

写完完整的计划之后，用新鲜的眼光再看一遍规格，拿计划对照它检查。这是你自己跑的检查清单——不是派一个子代理去做。

**1. 规格覆盖：** 快速过一遍规格里的每一节／每项要求。你能指出某个实现它的任务吗？把缺口列出来。

**2. 步骤扫描：** 每个步骤都必须让实现者恰好写出唯一一件合理的事，且不得携带更多东西：决定不了任何事的行是缺口，而签名和测试已经确定下来的函数体是抄写。两种都修。

**3. 类型一致性：** 你在后面的任务里用到的类型、方法签名和属性名，与你在前面任务里定义的一致吗？某个函数在第 3 个任务里叫 `clearLayers()`、到第 7 个任务里却叫 `clearFullLayers()`——这就是 bug。

**4. 评审重点：** 对规格暗示的每一类输入或失效模式，是否存在某个任务的测试会覆盖它？最可能坑到人的五个未被覆盖的，写进「评审重点」一节，并且那里每加一行，就要把对应的测试加到拥有那段代码的任务里。这一节为空，意味着你查过、确实没有，而不是你跳过了检查。

**5. 比例：** 把计划的长度和规格的长度比一比。一份比它实现的规格长出好几倍的计划，是程序的抄写，不是计划。如果代码块占了文档的大部分，就用签名、测试名和断言替换函数体，并检查每个步骤是否仍然没有歧义。

如果发现问题，就地改掉。不必重新评审——改完继续往前走。如果发现规格里的某项需求没有对应任务，就把任务补上。

## 执行交接

保存并自我检查完计划之后，把计划链接给你的搭档读。如果他们此前已经明确给出过执行方式，就请他们评审这份计划，确认它抓住了他们想要的东西；在实现之前等这次评审，然后采用既定的执行方式。否则，请他们评审计划，并在实现之前选择一种执行方式。

**当尚未给出执行方式时：**

**「计划已完成，并保存至 `docs/superpowers/plans/<filename>.md`。请评审这份计划。你更希望采用哪种执行方式？

- **子代理驱动** —— 由一个全新的子代理实现每个任务，并由一位全新的评审者在下一个任务开始前检查它，最后再做一次整分支评审。最彻底；代价是每个任务、每次评审都要一个全新的上下文。
- **原生（Native）** —— 我在本会话中亲自实现每一个任务，按这个宿主环境（harness）运行工作的方式来做，最后由一位使用最强模型的全新评审者检查整个分支。最便宜、最快；结束前没有独立评审。因为设计由计划承载，用中档的会话模型也能跑得很好。

对这份计划，我推荐 <两者之一>，因为 <用计划里的一句话说明：任务之间在多大程度上互相依赖对方的接口、一共有多少个任务、一旦有错发布出去代价有多大>。这份计划抓住你想要的东西了吗？我们该采用哪种方式？」**

**当执行方式已经给出时：**

**「计划已完成，并保存至 `docs/superpowers/plans/<filename>.md`。请评审这份计划。它抓住你想要的东西了吗？」**

**如果选择子代理驱动：**
- **必需的子技能：** 使用 superpowers:subagent-driven-development

**如果选择原生（Native）：**
- **必需的子技能：** 使用 superpowers:executing-plans
