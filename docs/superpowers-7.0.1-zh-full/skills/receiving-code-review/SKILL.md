# 接收代码评审

## 概览

代码评审需要技术评估，而不是情绪表演。

**核心原则：** 先验证再实现。先询问再假设。技术正确性优先于社交舒适。

## 应对模式

```
WHEN 收到代码评审反馈时：

1. READ：先把反馈完整读完，不做反应
2. UNDERSTAND：用自己的话复述要求（或直接问）
3. VERIFY：对照代码库的实际情况核对
4. EVALUATE：对 THIS 代码库来说，技术上站得住吗？
5. RESPOND：给出技术上的确认，或有理有据地反驳
6. IMPLEMENT：一次只做一项，逐项测试
```

## 禁止的回应

**绝不：**
- 「你说得完全对！」（明确违反指令文件）
- 「说得好！」/「反馈太棒了！」（表演式）
- 「我现在就来实现」（在验证之前）

**而是：**
- 重述技术要求
- 提出澄清问题
- 如果有误，用技术理由反驳
- 直接开始干活（行动 > 言语）

## 处理不清楚的反馈

```
IF 有任何一项不清楚：
  STOP —— 先什么都不要实现
  ASK：就不清楚的条目请求澄清

WHY：条目之间可能有关联。只理解一部分 = 实现出错。
```

**示例：**
```
你的搭档：「修复 1-6 项」
你理解 1,2,3,6。对 4,5 不清楚。

❌ WRONG：现在就实现 1,2,3,6，4,5 以后再问
✅ RIGHT：「我理解第 1,2,3,6 项。继续之前需要先澄清 4 和 5。」
```

## 按来源分别处理

### 来自你的搭档
- **可信** —— 理解之后就实现
- 范围不清楚时**仍然要问**
- **不要表演式赞同**
- **直接行动**，或给出技术上的确认

### 来自外部评审者
```
BEFORE（开始实现之前）：
  1. Check：对 THIS（这个）代码库来说技术上正确吗？
  2. Check：会破坏现有功能吗？
  3. Check：当前实现为什么这么写？
  4. Check：在 platforms/versions 上都能工作吗？
  5. Check：评审者理解完整上下文吗？

IF 建议看起来不对：
  用技术理由反驳

IF 无法轻松验证：
  直说：「没有 [X] 我不能验证。我应该 [investigate/ask/proceed] 吗？」

IF 与你的搭档先前的决定冲突：
  先停下来，与你的搭档讨论
```

**你的搭档的规则：**「外部反馈——保持怀疑，但要仔细核查」

## 对「专业」功能做 YAGNI 检查

```
IF 评审者建议「properly 实现」：
  在代码库里 grep 实际用法

  IF 没人用：「这个 endpoint 从没被调用过。要删掉吗（YAGNI）？」
  IF 有人用：那就好好实现
```

**你的搭档的规则：**「你和评审者都向我汇报。如果不需要这个功能，就不要加。」

## 实现顺序

```
FOR 多条反馈：
  1. FIRST：先把任何不清楚的地方澄清
  2. 然后按这个顺序实现：
     - 阻塞性问题（破坏、安全）
     - 简单修复（拼写、导入）
     - 复杂修复（重构、逻辑）
  3. 每项修复单独测试
  4. 验证没有回归
```

## 何时该反驳

在以下情况反驳：
- 建议会破坏现有功能
- 评审者缺少完整上下文
- 违反 YAGNI（用不到的功能）
- 对这个技术栈来说技术上不正确
- 存在遗留/兼容性原因
- 与你搭档的架构决策冲突

**如何反驳：**
- 用技术理由，而不是防御姿态
- 提出具体问题
- 引用可用的测试/代码
- 涉及架构时，让你的搭档参与

**如果你当众反驳会觉得不舒服：** 说出这种张力，然后把你看到的问题告诉你的搭档。他们会感谢你的坦诚。

## 确认正确的反馈

当反馈确实正确时：
```
✅「已修复。[Brief description of what changed]」
✅「抓得好——[specific issue]。已在 [location] 修复。」
✅ [Just fix it and show in the code]（直接修好，并在代码中展示）

❌「你说得完全对！」
❌「说得好！」
❌「谢谢你抓到这个！」
❌「谢谢你的 [anything]」
❌ ANY 任何表达感谢的说法
```

**为什么不道谢：** 行动胜于言辞。直接修好就行。代码本身就表明你听到了反馈。

**如果你发现自己正要写「谢谢」：** 删掉它。改为陈述修复内容。

## 得体地纠正自己的反驳

如果你反驳了，而且错了：
```
✅「你是对的——我查了 [X]，它确实会 [Y]。现在开始实现。」
✅「已核实，你是对的。我最初理解错了，原因是 [reason]。正在修复。」

❌ 长篇道歉
❌ 为自己当初的反驳辩解
❌ 过度解释
```

就事论事地陈述更正，然后继续。

## 常见错误

| 错误 | 修正 |
|---------|-----|
| 表演式赞同 | 陈述要求，或者直接行动 |
| 盲目实现 | 先对照代码库验证 |
| 批量处理却不测试 | 一次一项，逐项测试 |
| 假定评审者是对的 | 检查是否会破坏东西 |
| 回避反驳 | 技术正确性 > 舒适 |
| 部分实现 | 先澄清所有条目 |
| 无法验证却照做 | 说明限制，请求指示 |

## 真实示例

**表演式赞同（坏）：**
```
评审者：「删掉遗留代码」
❌「你说得完全对！我这就把它删掉……」
```

**技术验证（好）：**
```
评审者：「删掉遗留代码」
✅「我查一下……构建目标是 10.15+，这个 API 需要 13+。向后兼容得留着旧代码。当前实现的 bundle ID 写错了——是修它，还是放弃 13 以下的支持？」
```

**YAGNI（好）：**
```
评审者：「把指标跟踪实现到位，带数据库、日期筛选、CSV 导出」
✅「在代码库里 grep 过了——没有任何地方调用这个 endpoint。要删掉吗（YAGNI）？还是有我不知道的用法？」
```

**不清楚的条目（好）：**
```
你的搭档：「修复第 1-6 项」
你理解 1,2,3,6。对 4,5 不清楚。
✅「我理解第 1,2,3,6 项。开始实现前需要先澄清 4 和 5。」
```

## GitHub 线程回复

在 GitHub 上回复行内评审意见时，要在评论线程中回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是作为 PR 的顶层评论。
