# 系统化调试

## 概览

**核心原则：** 在尝试修复之前，始终先找到根因。只治症状的修复就是失败。

**违背这个流程的字面要求，就是违背调试的精神。**

## 铁律

```
没有根因调查，就绝不修复（NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST）
```

如果你还没有完成阶段 1，你就不能提出修复方案。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产环境中的 bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**尤其是在以下情况必须使用：**
- 时间压力下（紧急情况会让猜测变得诱人）
- 「就快速修一下」看起来很明显
- 你已经尝试过多次修复
- 上一次修复没起作用
- 你还没有完全理解这个问题

**以下情况不要跳过：**
- 问题看起来很简单（简单的 bug 也有根因）
- 你很赶时间（赶工必然带来返工）
- 经理要求「现在就修好」（系统化比乱撞更快）

## 四个阶段

你必须完成每个阶段，才能进入下一个阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们往往包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切的步骤是什么？
   - 它每次都会发生吗？
   - 如果不能复现 → 收集更多数据，不要猜

3. **检查最近的改动**
   - 有什么改动可能导致这个问题？
   - Git diff、最近的提交
   - 新增依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，先加诊断埋点：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo SET || echo UNSET)"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "IDENTITY in environment" || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这能揭示：** 哪一层失败（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误深入调用栈时：**

   完整的反向追踪技术见本目录下的 `root-cause-tracing.md`。

   **快速版：**
   - 坏值是从哪里来的？
   - 是谁用坏值调用了这里？
   - 一直向上追到源头
   - 在源头修，而不是在症状处修

### 阶段 2：模式分析

**先找到模式，再动手修：**

1. **找到可用的示例**
   - 在同一个代码库里找到类似的可用代码
   - 有什么可用的东西和坏掉的东西相似？

2. **对照参考实现**
   - 如果是在实现某种模式，完整阅读参考实现
   - 不要略读 —— 读每一行
   - 在应用之前完全理解这个模式

3. **找出差异**
   - 可用版本和坏掉的版本之间有什么不同？
   - 列出每一处差异，无论多小
   - 不要假设「那不可能有影响」

4. **理解依赖**
   - 它需要哪些其它组件？
   - 需要哪些设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与测试

**科学方法：**

1. **提出单一假设**
   - 清楚地说：「我认为 X 是根因，因为 Y」
   - 把它写下来
   - 要具体，不要含糊

2. **做最小测试**
   - 用尽可能小的改动来验证假设
   - 一次只动一个变量
   - 不要一次修多个东西

3. **继续之前先验证**
   - 有效吗？有效 → 进入阶段 4
   - 无效？提出新的假设
   - 不要在原有修复之上再叠加修复

4. **当你不懂的时候**
   - 说「我不理解 X」
   - 不要装作懂
   - 寻求帮助
   - 继续调研

### 阶段 4：实施

**修根因，不修症状：**

1. **创建会失败的测试用例**
   - 尽可能最简单的复现
   - 如果可能，写成自动化测试
   - 没有测试框架就写一次性测试脚本
   - 修复之前必须有
   - 使用 `superpowers:test-driven-development` 技能来编写规范的失败测试

2. **实施单一修复**
   - 针对已识别的根因
   - 一次只改一处
   - 不要做「顺手改一下」的改进
   - 不要夹带重构

3. **验证修复**
   - 测试现在通过了吗？
   - 有没有破坏其它测试？
   - 问题真的解决了吗？
   - 在声称成功之前，使用 `superpowers:verification-before-completion` 技能

4. **如果修复无效**
   - 停下来
   - 数一数：你已经尝试了几次修复？
   - 如果 < 3：回到阶段 1，带着新信息重新分析
   - **如果 ≥ 3：停下来，质疑架构（见下面的第 5 点）**
   - 没有架构层面的讨论，不要尝试第 4 次修复

5. **如果 3 次以上修复都失败：质疑架构**

   **表明存在架构问题的模式：**
   - 每次修复都在不同位置暴露出新的共享状态、耦合或问题
   - 修复需要「大规模重构」才能落地
   - 每次修复都在别处制造新症状

   **停下来，质疑根本假设：**
   - 这个模式根本上是合理的吗？
   - 我们是不是「纯粹靠惯性在硬撑」？
   - 应该重构架构，还是继续修症状？

   **在尝试更多修复之前，与你的搭档讨论**

   这不是一次失败的假设 —— 这是错误的架构。

## 危险信号 —— 停下来，按流程走

如果你发现自己正在这样想：
- 「先快速修一下，之后再调查」
- 「先改改 X 看看行不行」
- 「一次改多处，然后跑测试」
- 「跳过测试，我手动验证一下」
- 「大概是 X，我来修一下」
- 「我没完全弄懂，但这个可能行」
- 「模式说该用 X，但我换个方式改」
- 「主要问题有这些：[不做调查就直接列修复方案]」
- 在追踪数据流之前就提出解决方案
- **「再试一次修复」（在已经试过 2 次以上时）**
- **每次修复都在不同地方暴露新问题**

**以上任何一条都意味着：停下来。回到阶段 1。**

**如果 3 次以上修复都失败了：** 质疑架构（见阶段 4.5）

## 你的搭档暗示你做错了的信号

**留意这些纠正：**
- 「不是没发生吗？」—— 你没验证就假设了
- 「这能给我们看……吗？」—— 你本该加上证据收集
- 「别猜了」—— 你在不理解的情况下提出修复
- 「狠狠想想这个」—— 质疑根本假设，而不只是症状
- 「我们卡住了？」（沮丧）—— 你的方法不管用

**看到这些时：** 停下来。回到阶段 1。

## 常见自我合理化

| 借口 | 现实 |
|--------|---------|
| 「问题很简单，不需要流程」 | 简单问题也有根因。流程对简单 bug 也很快。 |
| 「紧急情况，没时间走流程」 | 系统化调试比瞎猜乱撞更快。 |
| 「先试试这个，之后再调查」 | 第一次修复会定下模式。从一开始就做对。 |
| 「等确认修复有效后我再写测试」 | 没测试的修复站不住脚。测试先行才能证明它。 |
| 「一次改多处能省时间」 | 无法判断是哪处起了作用。还会引入新 bug。 |
| 「参考实现太长，我照着改一下」 | 一知半解必然带来 bug。完整读一遍。 |
| 「我看出了问题，我来修」 | 看到症状 ≠ 理解根因。 |
| 「再试一次修复」（在 2 次以上失败后） | 3 次以上失败 = 架构问题。质疑模式，不要再修。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读错误、复现、检查改动、收集证据 | 理解是什么（WHAT）和为什么（WHY） |
| **2. 模式** | 找到可用示例、对比 | 找出差异 |
| **3. 假设** | 形成理论、最小化测试 | 假设被证实，或提出新假设 |
| **4. 实施** | 创建测试、修复、验证 | bug 已解决，测试通过 |

## 当流程表明「没有根因」时

如果系统化调查表明问题确实是环境性的、依赖时序的或外部的：

1. 你走完了整个流程
2. 记录你调查了什么
3. 实施合适的处理（重试、超时、错误提示）
4. 为后续调查添加监控与日志

**但是：** 95% 的「没有根因」案例，都是调查不完整。
