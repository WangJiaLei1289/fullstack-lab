<SUBAGENT-STOP>
如果你是作为子代理被派去执行某个具体任务的，忽略本技能。
</SUBAGENT-STOP>

<EXTREMELY-IMPORTANT>
如果你认为某个技能有哪怕 1% 的可能适用于你正在做的事，你绝对必须调用该技能。

只要某个技能适用于你的任务，你就没有选择的余地。你必须使用它。

这没有商量的余地。你无法靠自我合理化绕开这一点。
</EXTREMELY-IMPORTANT>

## 规则

**在做出任何回应或采取任何行动之前，先调用相关或被要求的技能**——包括澄清式提问、浏览代码库、查看文件。如果事后发现它不适合当前情况，你不必继续用下去。

**进入计划模式之前：** 如果你还没有做过头脑风暴，先调用 brainstorming 技能。

然后宣告 "Using [skill] to [purpose]"（我正在使用 [skill] 技能来做 [purpose]），并严格照该技能执行。如果它有检查清单，就为每一项建一个待办。

## 技能优先级

当多个技能都适用时，流程类技能优先——它们先定下做法，再由实现类技能（frontend-design 等）去落地。头脑风暴和系统化调试是 Superpowers 最常用的流程类技能，但这条规则对任何流程类技能都成立。

- 「我们来做一个 X」 → 先 superpowers:brainstorming，再上实现类技能。
- 「修一下这个 bug」 → 先 superpowers:systematic-debugging，再上领域技能。

## 危险信号

出现下面这些念头就意味着停下来——你正在自我合理化：

| 念头 | 现实 |
|---------|---------|
| 「这只是一个简单的问题」 | 提问也是任务。先查技能。 |
| 「我需要先了解更多上下文」 | 查技能要在澄清式提问之前。 |
| 「让我先看看代码库」 | 技能会告诉你该怎么看。先查。 |
| 「我可以快速翻一下 git/文件」 | 文件里没有对话上下文。先查技能。 |
| 「让我先收集信息」 | 技能会告诉你该怎么收集信息。 |
| 「这件事用不着什么正式技能」 | 只要有技能存在，就用它。 |
| 「我记得这个技能」 | 技能会演进。读当前版本。 |
| 「这不算任务」 | 行动 = 任务。先查技能。 |
| 「这个技能太重了」 | 简单的事也会变复杂。用它。 |
| 「我就先把这一件事做了」 | 做任何事之前先查。 |
| 「这感觉很有产出」 | 没有章法的行动是浪费时间。技能能避免这一点。 |
| 「我知道那是什么意思」 | 懂这个概念 ≠ 会用这个技能。调用它。 |
