维度：质量证据

用流程自己的说法来检验流程。这不是代码评审；不要评价会话产出的代码。

1. 测试：每一次测试运行（包含 `test`、`pytest`、`npm test`、`cargo test`、`go test`、`bats`、`bash tests/…` 的命令，或指令文件中点名的项目测试运行器）及其结果行。报告失败的运行，以及助手接下来做了什么。
2. 断言背后的验证：找出声称完成、已修复、通过、已验证、可用、完整这类助手文本。对每一条，在同一轮次内往回找能证明它的工具结果（一次测试运行、一段命令输出、一个 diff）。报告在该轮次内没有任何支撑结果的断言。
3. 提交：每一次 `git commit` 及其提交信息；把每条提交信息与前面轮次中的工具调用做对比。报告两类情况：提交信息声称做了某项工作，但没有任何工具调用执行它；以及实际做了工作、却从未提交，而已达成一致的计划说会提交。
4. 评审反馈：当评审者（人类或子代理）提出意见时，找到对应的回应。报告被认可但未处理的意见，以及被驳回却没有说明理由的意见。
5. 验收标准：如果案例文件的问题陈述或已达成一致的计划列出了标准，就逐条报告为已满足 / 未满足 / 未检查，并附证据行。
