# 修复循环

属于 superpowers:subagent-driven-development 技能的一部分。任务评审报告了规格 ❌、一个 Critical 或 Important 发现项，或者一个你已确认为真实缺口的 ⚠️ 事项。

循环开始之前，有两条路会立刻离开循环：

- 边做边把 Minor 发现项记进进度账本
  （`Task <N>: minor (deferred): <one-liner>`），并让最终的分支级评审指向这份清单，好让它甄别哪些必须在合并前修掉。没人看的汇总等于静默丢弃。Minor 发现项永远不进入循环。
- 一个被标为「计划强制要求」的发现项——以及任何与计划文字相冲突的发现项——由你来裁定：拿这条发现项与计划文字权衡，以规格为约束性权威做决定，并在动手之前把裁定记入账本。不要因为计划强制要求就驳回这条发现项，也不要在没有记录裁定的情况下分派一个与计划相矛盾的修复。
其余一切都进入循环。一轮修复 = 一次修复分派 + 一次定范围的复审。每个任务最多五轮：

**第 1-3 轮——恢复原来的实现者。** 把未结的发现项逐字发给它。它的上下文完好：它了解这个任务、这些代码，以及它自己当初的选择。如果你的宿主环境无法再给一个运行中的子代理发消息，就分派一个全新的实现者，带上简报路径、报告文件路径和这些发现项——无论哪种方式，报告文件都是持久记忆。

**第 4-5 轮——用更强的模型分派一个全新的实现者**（按 SKILL.md 的模型选择），带上简报路径、报告文件路径、未结的发现项，以及这段定调语：「先前有实现者尝试这个任务 [N] 次；现在归你负责。读报告文件，看看都试过什么。」一个扛过三次「恢复」的循环，通常意味着实现者看不见自己的问题——换双眼睛和提升能力，一步到位。

**每一轮，无论哪种方式：** 实现者修复、重跑覆盖被改动代码的测试、把修复报告追加到同一个报告文件，并返回那份简短契约。在重新分派评审者之前，确认修复报告里包含覆盖测试、所运行的命令与输出；三者齐了再分派复审。在修复消息里点名覆盖测试的文件——一行修复不需要整套测试。

**复审是定范围的。** 运行 `bash scripts/review-package PLAN_FILE FIX_BASE HEAD`，其中 FIX_BASE 是上一次评审看到的 head，并分派
[re-review-prompt.md](../re-review-prompt.md)，带上发现项清单、简报、报告文件以及打印出的 diff 路径。复审者对每条发现项给出 ADDRESSED 或 NOT ADDRESSED 的判定，并且只标记修复 diff 中新增的破坏。修复 diff 中新增的 Critical/Important 破坏并入未结发现项清单。范围外的观察作为延后次要项记入账本——它们绝不延长循环。

**每一轮之后，** 往账本追加：
`Task <N>: fix round <R>/5 (<X> addressed, <Y> open — <finding one-liners>; commits <a7>..<b7>)`

绝不要在控制器会话里自己修发现项——你的上下文要留干净来做事协调，而且控制器亲手修的代码会跳过评审。

**断路器。** 当第 5 轮的复审仍然留下未结发现项时，停止分派。每条未结发现项由你自己裁定——你掌握着评审者所没有的计划与跨任务上下文：

- **评审者错了，或者这一点可争议：** 搁置它——
  `Task <N>: parked — <finding> — Ruling: <why the code stands>`。最终评审会同时看到双方。
- **是真的，但下游没有东西建立在它之上：** 用同样的方式搁置，裁定里写明它是真的、但被延后。
- **是真的且承重**——后续任务建立在它之上，或者它暴露了计划缺陷：给出能最小程度解除依赖工作阻塞的改动，记入账本为 `Task <N>: Ruling: <finding> — <what you decided and why>`，并把它带进下一个任务的分派。静默地搁置一个结构性失败，等于让每个依赖任务都建立在其上。只有当缺陷使所有前进路径都成了猜测时才停下。

只在上限处裁定。为了结束循环而提前裁定，是换了个名字的预判。每一次裁定都是一条账本记录——静默丢弃是被禁止的。
